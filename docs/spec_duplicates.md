# レシート OCR: 重複したレシートの見分け 仕様 1.2

対象は直下の `src/`（Python の Cloud Run Job）。クレカ明細（`クレカ明細自動仕訳/`）には触れない。改良の順の ③（重複チェック）の一部。前提は `docs/spec_read_quality.md` 1.6（既定は 3.5-flash-lite・v2・両読み・考える量 low）。

## 1. 目的

同じレシートを二度スキャンしたものを、二重に記帳しない・見て分かるようにする。

- 同じファイルの中の二重スキャン（例: 3 ページの PDF の 2・3 ページ目が同じ駐輪場の領収書）は、記帳したうえで注記する。
- 別のファイルの二重スキャン（例: 同じレシートを 2 回撮った写真）は記帳しない。ファイル名に【重複】を付け、重複元が分かるようにする。

## 2. 利用者の決定（2026-11-20）

- **同じ証憑かの判断の原則**: 読み取れる情報から別々のレシート・領収証だと示せれば別の証憑として記帳する。示せなければ重複とみなす。レシートに時刻の記載が無ければ、時刻は判断に使わない。
- **同じファイルの中**: 同じ証憑とみなした 2 枚目以降の行は記帳し、エラー詳細の欄（O 列）に「同じ内容の行があります（二重スキャンかも）」と書く。要確認には回さない。
- **別のファイル**: 同じ証憑とみなしたレシートは記帳しない。
  - ファイルの全部のレシートが重複なら、ファイル名の頭に `【重複】` を付ける。
  - 一部だけが重複なら、重複でないレシートだけを記帳する。
  - 重複元のファイルへのリンクを、Drive のそのファイルの「説明」欄に書く。

## 3. 同じ証憑かの判断

2 枚のレシート A・B について、次の全部を満たすとき「同じ証憑」とする。

1. 日付がどちらも `YYYY-MM-DD` で読めていて、等しい。
2. 金額がどちらも 1 以上の整数で読めていて、等しい。
3. 店名が合う。合い方は `docs/spec_model_compare.md` §7 の店名の合い方と同じ（NFKC → 小文字 → 会社の種類の言葉と空白・記号を除く → 等しいか、短い方が 2 字以上で長い方に含まれる）。どちらかが空なら合わない。
4. 別のレシートだと示せない。次のどれかに当たれば「示せる」:
   - 時刻がどちらにも読めていて、違う。
   - 番号（§4 の `receipt_no`）がどちらにも読めていて、そろえた値が違う。

日付か金額がどちらかで読めていなければ、同じ証憑とはしない（判断しない）。片方にしか時刻・番号が無いときは、その欄は判断に使わない（4 に当たらない）。

## 4. AI に読ませる欄（指示文 第 2 版）

第 2 版の出力の明細に 2 つの欄を足す。第 1 版は 1 字も変えない（第 1 版で読んだ明細は、2 つの欄が読めていないものとして扱う）。

- `time`: 支払い・発行の時刻を `HH:MM`（24 時間）。駐車場のように入庫と精算の時刻があるときは精算（支払い）の時刻。書いていなければ空。
- `receipt_no`: そのレシート 1 枚ごとに変わる番号（レシート番号・管理番号・取引番号・伝票番号・領収証 No.・精算 No.・送り状番号など）。いくつもあるときは、この並びで先に当たるもの 1 つ。店の登録番号（T＋13 桁）・電話番号・車室番号・レジ番号・担当者番号は入れない。書いていなければ空。
- そろえ方（比べるとき）: `time` は `H:MM` も `HH:MM` に。`receipt_no` は NFKC にして、空白と `-` `‐` `－` `ー` を除き、英字を大文字に。
- 両読みの照らし合わせ（`reconcile`）には 2 つの欄を使わない（今の決め方のまま）。表へ書く明細の `time`・`receipt_no` は画像からの値、画像からが空なら文字からの値。
- 指示文を変えたあと、比較（`AI_PROMPT_VERSION=v2`、`COMPARE_MODELS=gemini-3.5-flash-lite`、新しいラベル、全部）を 1 回流し、日付・金額・税率・店名の正答率が前回（`v2full-20261120` の low）より下がっていないことを確かめる。

## 5. 同じファイルの中

- 1 つのファイルで読めた明細を番号の順に見て、前の明細と同じ証憑（§3）なら、その明細の行の O 列（`error_detail_column`）に `同じ内容の行があります（二重スキャンかも）` と書く。最初の 1 枚には書かない。
- 自動の行（通常の行）にも ※ の行にも書く。※ の行で O 列に既に文があれば、`／` でつないで後ろに足す。
- 記帳する・しない、`【済】` を付ける・付けないは今のまま（注記だけ）。

## 6. 別のファイル

### 6.1 照らす相手（記録）

- 照らす相手は、同じ顧客の出納帳の「処理管理」タブに、§6.4 の欄つきで記録された明細のうち、状態が `success`・`low_confidence`・`manual_entry`・`written`・`reserved` のもの（記帳した・記帳中の明細）。
- 同じファイル ID の記録は相手にしない（同じファイルの読み直しは §5 と今の重複防止に任せる）。
- この機能を入れる前の記録（§6.4 の欄が空）は相手にしない。
- 同じ実行の中で先に処理したファイルの明細も相手にする（処理の順で先のものが元、後のものが重複）。

### 6.2 重複の明細

- 記帳する前に、ファイルの明細を 1 枚ずつ §6.1 の相手と照らす。同じ証憑（§3）があれば、その明細は重複とする。
- ※ になる明細（両読みで合わなかった明細）も照らす。照らす値は画像からの値（画像からが空なら文字からの値）。
- 重複の明細は出納帳に書かない（行も予約しない）。処理管理には状態 `duplicate` の記録を 1 行書く（§6.4 の欄と重複元も入れる）。`duplicate` は「済んだ明細」として扱い、次の実行で読み直さない（`get_processed_keys` に入れる）。

### 6.3 ファイルの扱い

- **全部が重複**: 出納帳に何も書かない。ファイル名の頭に `【重複】` を付ける（`【済】` は付けない）。説明欄に重複元を書く。
- **一部が重複**: 重複でない明細を今までどおり記帳する。今の決まりで `【済】` が付く条件を満たせば `【済】` を付ける。説明欄に重複元を書く。
- **重複なし**: 今のまま。
- `【重複】` で始まるファイルは、`【済】` と同じく読む対象から外す（`excluded_file_name_prefixes` と `_ALREADY_DONE_PREFIXES` に足す）。
- 説明欄: 今の説明を消さず、後ろに 1 行ずつ足す: `重複: <この明細の番号> 枚目 → 重複元 <ファイル名> <https://drive.google.com/file/d/<ID>/view>（<重複元の番号> 枚目）`。同じ文が既にあれば足さない。
- 名前の変更・説明の書き込みに失敗しても、記帳と処理管理の記録は戻さない（`【済】` を付けられなかったときと同じ扱い。ログに出す）。次の実行では `duplicate` の記録があるので二重に記帳しない。

### 6.4 処理管理の欄

「処理管理」タブの見出しの右（L 列から）に 6 つ足す: `receiptDate` / `receiptTime` / `amount` / `vendor` / `receiptNo` / `duplicateOf`。

- 明細を記帳する（予約する）ときに、その明細の日付・時刻・金額・店名・番号（§4 のそろえる前の値）を書く。`duplicateOf` は重複の明細だけ: `<重複元のファイル ID>:<重複元の番号>`。
- 今ある処理管理のタブで L1 から右が空なら、見出しを書き足す。見出しが既にあり、この並びと違えば、その顧客の処理を止めて何も書かない（エラーを記録する）。

## 7. 安全の条件（変えない。すべてテストで確かめる）

- D1: 重複と判断したときだけ記帳しない。§3 を満たさない明細は今までどおり記帳する（日付・金額が読めない明細を重複にしない）。
- D2: 同じファイルの中の重複は記帳する（注記だけ）。
- D3: 1 枚の明細を、記帳と `duplicate` の両方にしない。重複の明細のために出納帳の行を予約しない。
- D4: `【重複】` のファイルは次の実行で読まない。`duplicate` の明細は次の実行で読み直さない。
- D5: `dry_run`・`validate` では、名前・説明・処理管理・出納帳のどれにも書かない（判断の結果はログに出す）。
- D6: 処理管理の見出しが違うときは、その顧客の分は何も書かずに止まる。
- D7: 第 1 版の指示文・`text_first` の流れの呼び出しの順と回数は変えない（重複の判断は、読んだ後・書く前に足すだけ）。
- D8: クレカ明細・比較モード（`RUN_MODE=compare`）の動きは変えない。

## 8. テスト（pytest。ネットワークを使わない。API・Drive・Sheets はすべて偽物）

- §3: 日付・金額・店名が同じで時刻も番号も無い → 同じ／時刻が両方にあり違う → 別／時刻が片方だけ → 同じ／番号が両方にあり違う → 別／番号のそろえ方（空白・ハイフン・全角）／店名の合い方（株式会社の有無・支店名の有無）／日付か金額が読めない → 判断しない／金額が違う → 別。
- §5: 同じファイルの 2・3 枚目が同じ → 2・3 枚目の O 列に注記、1 枚目には無し／時刻が違う 3 枚（20 円 × 3、時刻 17:32・17:33・17:34）→ 注記なし／※ の行の O 列の既存の文に足す。
- §6: 別ファイルの記録と同じ → 記帳しない・`duplicate` の記録・`【重複】`・説明欄／一部だけ重複 → 残りは記帳・`【済】`・説明欄／同じ実行で先のファイルと同じ → 後のファイルが重複／同じファイル ID の記録は相手にしない／欄が空の古い記録は相手にしない／`error`・`expired` の記録は相手にしない／`【重複】` のファイルを読まない／`duplicate` を済んだ明細として扱う／名前の変更に失敗しても記帳を戻さない／説明欄に同じ文を二度足さない。
- §6.4: 見出しが無い → 足す／同じ → そのまま／違う → 止まって何も書かない。
- 指示文: 第 2 版に `time`・`receipt_no` の説明がある。第 1 版が今の文字列と等しい。応答に 2 つの欄が無くても読める。
- D5・D7・D8。今あるテストは変えずに全部通す（見出しの数を固定しているテストは直してよい。直した所は報告する）。

`ruff check src/ tests/` と `ruff format --check src/ tests/` を通す。

## 11. 監査の直し（1.1）

Opus xhigh の監査（`bf02803..a3add71`、C0・H2・M5・L5）を受けて、次のとおり決める。§3〜§8 と食い違えばこの節が勝つ。

- 11.1（H1）処理管理と照らし合わせに使う値: 両読みで、画像からの明細と組になった文字からの明細があるときだけ、画像からが空の `time`・`receipt_no` を文字からで埋める。日付・金額・店名は画像からの値だけを使う（文字からで埋めない）。組にならなかった明細は画像からの値だけ。並びの位置で文字からの明細を借りない。`text_first` は読んだ明細の値だけ。
- 11.2（M1）時刻のそろえ方: `H:MM`・`HH:MM`・`HH:MM:SS`（秒は捨てる）・`17時32分`・`17時`（分 00）・`午前`／`午後`（`AM`／`PM`）付きを受ける。時は 0〜29（深夜の営業日の書き方）。両方に時刻の文字があり、どちらかがそろえられないときは、NFKC にして空白を除いた元の文字を比べ、違えば「別」とする（そろえられないことを「時刻なし」にしない）。
- 11.3（M2）両読みで前の回の印がある（読み直しの守り `_has_numbered_marks` が効く）ファイルでは、別のファイルとの重複で外さない。未処理の明細は今までどおり読み直しの ※ の行にし、別のファイルと同じ証憑なら O 列に `別のファイルに同じ内容の明細があります（重複元 <ファイル名> <番号> 枚目）` を `／` でつないで足す。`duplicate` の記録・`【重複】`・説明欄は書かない。
- 11.4（M3）L〜P は予約の追記（`reserve_rows`）と同じ 1 回の書き込みで A〜Q として書く（後から別に書かない）。同じファイルの中の重複の注記は、自動の行でも出納帳の行を書く 1 回の書き込み（`write_cashbook_row`）に入れる。
- 11.5（M4）`ensure_log_sheets_exist` は顧客ごとに 1 回だけ、マスターの「処理中」より前に呼ぶ（見出しが違えば、その前に止まる。dry_run では書かない）。顧客の始めに読む処理管理（`get_processed_keys` と照らす相手）は、タブがあるのに読めない（429 などの失敗）ときは例外にして、その顧客を止める（空として続けない）。タブが無い（dry_run の新しい出納帳）ときだけ空。ほかの所の読み方は変えない。
- 11.6（M5）全部が重複のファイルでも、`duplicate` の記録が 1 件でも書けなかったら、`【重複】` も説明欄も付けない（次の実行でやり直す）。一部が重複のときも、書けなかった明細の説明の行は足さない。
- 11.7（L1）`text_first` の金額の再抽出は、記帳する明細（重複でない明細）に金額の NG があるときだけ呼ぶ。全部が重複のファイルでは呼ばない（重複の明細のために AI を呼ばない。D7 の例外としてここに記す）。重複の判断は、再抽出の前の値で行う。
- 11.8（L2）`【重複】` で始まるファイルは、環境変数 `EXCLUDED_FILE_NAME_PREFIXES` の値にかかわらず読む対象から外す。`.env.example` と README の既定の書き方に `【重複】` を足す。
- 11.9（L3）戻すとき: この機能より前のコードに戻すと、`【重複】` のファイルと `duplicate` の明細が読み直されて記帳される。戻すときは Cloud Run の環境変数に `EXCLUDED_FILE_NAME_PREFIXES=[済],【済】,【重複】` を入れる（README の戻し方に書く）。
- 11.10（L4・記録だけ）一部の明細が前の回に済み、残りが全部重複のファイルは、`【重複】` も `【済】` も付かず、毎回読み直される（記帳はしない。費用だけ）。今の `【済】` の作りと同じ。
- 11.11（H2・L5）テスト: 本番の既定は両読みなので、§5・§6・D1・D3・D5・11.1・11.3・11.6 を両読みでも確かめる。記帳 → 処理管理の L〜P → 次の実行で照らす相手として読む → 後のファイルが重複、を通しで確かめる。比較の道具は、score が「答え_複数」の行を実際に使うこと・`メモ` より右の列を読まないことを確かめる。

## 12. 直しの監査の直し（1.2）

直しの差分（`024d3af..e3b080e`）の Opus xhigh の監査（C0・H0・M1・L9）を受けて決める。§11 と食い違えばこの節が勝つ。
