# レシート OCR: 審判の形（形 C）仕様 1.1

対象は直下の `src/`（Python の Cloud Run Job）の比較モード（`RUN_MODE=compare`）だけ。本番の流れ・クレカ明細（`クレカ明細自動仕訳/`）には触れない。土台は `docs/spec_reader_compare.md`（読み手の比較と形。以下「読み手の仕様」）。そこに書いてある決まりを変えずに足す。

## 1. 目的

2026-11-21 の利用者の決定: 「判断だけを返す型」（Decisions API）を **審判** として比較に足し、156 本の答えで測る。形を決めるのはその結果を見てから。

今の本番（両読み）は、主の読み手の **画像から** と **文字から** の日付・金額が合った明細だけを自動にする。合わない明細は、どちらが正しいかシステムに分からないので要確認になる。形 B は、もう 1 人の読み手に全部を読み直させて確かめる。形 C は、**合わない明細だけ**について、画像と候補の値を審判に見せて「どれが正しいか」を選ばせる。

| 形 | 中身 |
|---|---|
| C（審判 J・下限 θ） | 今（両読み）のまま。合わない明細があるファイルだけ審判 J を 1 回呼ぶ。審判が **主の画像からの値** を、確からしさ θ 以上で選んだ明細を自動にする |

- 表に入る値は、どの場合も主の画像からの読み（Ib）。**審判は値を作らない・直さない**。変えられるのは「要確認 → 自動」だけ。
- 審判の候補: `gemini-decision-1`（Google の Decisions API）と `gpt-6-luna`（OpenAI の Decisions API）。どちらも入力 100 万トークン 0.10 ドル・出力 0（2026-11-21 に公式のページで確認）。
- やり方は読み手と同じ: 審判の答えを表に残し、形の成績は **API を呼ばずに後から計算する**（下限 θ を変えても呼び直さない）。

分かっている弱み（測って確かめる）: 候補から選ぶだけなので、主の画像からが誤りで文字からも誤りのときは「どれでもない」を選べるかどうかに掛かる／両方の読みが同じ誤りをした明細（食い違わない誤り）は審判に回らない／公式に「計算しない・何段もの推論をしない」とある／日本語の手書きでの成績は公表が無い。

この仕様に入れない: 本番の流れを変えること（形が決まった後の別の仕様）。B と C を重ねる形。PDF を画像にする処理（§6.3）。

- **J8 式にならない**: 新しく書く値もすべて `valueInputOption=RAW`。

## 5. collect の変更

### 5.1 審判の回（読み取りの回の後、形の計算の前）

今の処理（`COMPARE_MODELS`・`COMPARE_READERS` の読み取りと表への書き込み）が終わった後に行う。時間の予算（`COMPARE_TIME_BUDGET_SECONDS`）を超えていたら審判の回は始めず、ログに書く（続きからで行う）。

1. 「結果_<ラベル>」「OCR_<ラベル>」を読み、形の計算と同じ関数（`forms.build_inputs`）でファイルごとの Ib・Tb・OCR の文字を作る。**今回読んだ値をメモリから使わない**（続きからでも同じ結果にするため）。
2. ファイルごとに D0 = `reconcile(Ib, Tb, OCR の文字)`。**Ib が空でなく、D0 に合わない明細が 1 つでもある**ファイルが対象（形 B の「呼ぶ」と同じ条件。同じ関数を使う）。`COMPARE_MAX_FILES` があれば、その範囲のファイルだけ。
3. 対象のファイル × 審判ごとに、済んでいなければ 1 回呼ぶ。済みの決め方は今と同じ（方式 `審判` の一番下の行が `失敗:api_error`・`失敗:file_error` でなければ済み）。
4. 対象のファイルは Drive から取り直す（審判ごとに取り直さない。1 ファイル 1 回）。Vision は呼ばない。
5. やり直し（429・5xx・529 は 10・30・60 秒で最大 3 回）・待ち時間の上限（`effective_request_timeout`）・並べ方（`COMPARE_MAX_WORKERS`）・途中で時間切れになったら残りを呼ばない、は読み手と同じ。1 つの審判の失敗はその行だけに留める（ほかの審判・ほかのファイルは続ける）。
6. 行は「結果_<ラベル>」に足す（§5.3）。その後に形の計算（§7）。

型の有無は確かめない（Decisions の型は一覧の API に出るとは限らない）。型名の誤りは最初の呼び出しの 404 で分かる: **404 が返った審判は、その回の残りのファイルを呼ばず**、ログに `使えない審判` と書く（行は `失敗:api_error`。続きからでやり直す）。

### 5.2 質問の作り方（純粋な関数。`judges.build_questions(Ib, Tb, D0, 明細の店名)`）

D0 で合わなかった Ib の明細 i（0 始まり）ごとに:

- 質問を作らない明細（要確認のまま）: Ib の金額が 1 以上の整数でない・日付が実在する `YYYY-MM-DD` でない。
- **金額の質問 `a<i>`**（選ぶ）。候補は次を順に集め、重複を除き、多くても 6 個:
  1. Ib[i] の金額
  2. D0 の理由が「先頭の桁の読み違いの疑い」のとき、Ib[i] の金額の先頭の 1 桁を除いた数（1 以上なら）
  3. Tb のうち D0 で組にならなかった明細の金額（1 以上の整数。Tb の並び順）
  4. `other`
- **日付の質問 `d<i>`**（選ぶ）。候補: Ib[i] の日付 → Tb のうち組にならなかった明細の日付（実在する日付だけ。並び順）→ `other`。重複を除き、多くても 6 個。
- 候補の鍵: 金額は区切りの無い 10 進の数字（例 `12300`）、日付は `YYYY-MM-DD`、どれでもないは `other`。
- D0 に「明細数要確認」（文字からの件数が多い）があるファイルには、**枚数の質問 `n`**（はい・いいえ）を足す: 「レシート・領収書は全部でちょうど N 枚か」（N = Ib の明細の数）。
- 質問を作る明細が 20 を超えるファイルは呼ばない（行は `失敗:too_many_items`。済みとして扱う）。質問が 1 つも無いファイルは呼ばない（行は作らない）。

文（日本語。版の名前は `judge-1`。変えたら版の名前も変える）:

- 共通の入力の文（ファイルの前に置く）: 「次の画像または PDF には、日本のレシート・領収書が 1 枚以上写っています。質問ごとに、指定したレシートについて答えてください。合計金額は、値引きと消費税を含めて実際に支払った金額です（小計・お預かり・お釣り・ポイントではありません）。日付は発行日・利用日です（お届け日・有効期限・印刷日ではありません）。」
- どのレシートか: Ib の明細が 1 つなら「このレシート」。2 つ以上なら「上から（ページ順に）<i+1> 番目のレシート」に、店名（`明細JSON` の `v`）が空でなければ「（店名は「<v>」と読めます）」を足す。店名は 40 字で切り、改行を空白にする。
- 金額: 「<どのレシートか>について、支払った合計金額（円）はどれですか。」候補の説明は「<3 桁区切り> 円」、`other` は「どの金額でもない、または読み取れない」。
- 日付: 「<どのレシートか>について、日付はどれですか。」候補の説明は「<Y>年<M>月<D>日」、`other` は「どの日付でもない、または読み取れない」。
- 枚数: 「この画像または PDF に写っているレシート・領収書は、全部でちょうど <N> 枚ですか。」

### 5.3 審判の行（「結果_<ラベル>」。見出しは変えない）

1 行 = 1 ファイル × 1 審判。`型` = 審判の型名、`方式` = `審判`。

- `結果`: `成功`／`失敗:api_error`（HTTP のエラー・つながらない）／`失敗:bad_response`（返りが §6.4 の形でない。やり直さない）／`失敗:unsupported_mime`／`失敗:too_large`／`失敗:empty_content`／`失敗:too_many_items`／`失敗:file_error`（そのほかの例外）。
- `件数` = 質問の数、`入力トークン`・`出力トークン`（0）・`応答ms`・`再試行`・`推定費用USD`（今の式。単価は §8）、`設定` = `provider=<google か openai>, judge, resolution=<値かなし>, prompt=judge-1`、`エラー詳細`（鍵を伏せる）。
- `生の応答`: 返りの `answers` を JSON の文字にしたもの（長ければ今の決まりで切る）。
- `明細JSON`: 形の計算の材料（JSON のオブジェクト。キーの並びは固定）:

```json
{"judge": 1,
 "base": [["2025-01-15", 12300]],
 "count": {"asked": 1, "p": 0.97},
 "items": [{"i": 0,
            "a": {"options": ["12300", "12800", "other"], "choice": "12300", "confidence": 0.93},
            "d": {"options": ["2025-01-15", "other"], "choice": "2025-01-15", "confidence": 0.99}}]}
```

  `base` は審判に見せたときの Ib の全部の明細（日付・金額。読めていない所は null）。`count` は枚数の質問をしたときだけ（`p` は「はい」の確率）。`items` は質問を作った明細だけ。`日付`・`合計金額` などの明細の欄は空のまま。

### 5.4 ほかの計算は審判の行を数えない

方式 `審判` の行は、集計タブ・`score` の正答率・読み手の一覧（`forms.reader_labels`）・「違い」の数え方に入れない（今あるテストの結果が 1 つも変わらないこと）。

## 6. 審判の呼び出し（`src/compare/judges.py`）

### 6.1 共通

- SDK は使わず、`httpx` で公式の REST を呼ぶ（今の `google-genai` 1.x には Decisions が無く、3.2 以上が要る。本番も使う SDK の主番号は、この仕様では上げない）。`httpx` はもう入っている（SDK 3 つの依存）ので、`requirements.txt` には今入っている版の主番号の範囲で 1 行足すだけ。
- 自動のやり直しはしない（やり直しは比較の道具が数える）。待ち時間の上限は `effective_request_timeout`。
- `httpx` の例外の文には URL が入ることがある。鍵は URL に入れないが、`エラー詳細` とログへ出す前に今の伏せ方（R4・読み手の仕様 §14.4）を必ず通す。つながらない・時間切れは `error_code=503`（やり直す）。
- 使える種類は読み手と同じ 4 つ（`image/jpeg`・`image/png`・`image/webp`・`application/pdf`）。それ以外は呼ばずに `unsupported_mime`、空なら `empty_content`。
- ファイルは base64（改行なし）。共通の入力の文を先、ファイルを後に置く。

### 6.2 Google（`gemini-decision-…`。2026-11-21 に公式のページ「Decisions API」で確認）

- `POST https://generativelanguage.googleapis.com/v1beta/decisions`、ヘッダー `x-goog-api-key: <GEMINI_API_KEY>`・`Content-Type: application/json`。
- 本文: `{"model": 型名, "input": [{"type": "text", "text": 共通の文}, <ファイル>], "questions": {<鍵>: <質問>, …}}`
  - 画像: `{"type": "image", "data": <base64>, "mime_type": <MIME>, "resolution": <COMPARE_JUDGE_IMAGE_RESOLUTION>}`
  - PDF: `{"type": "document", "data": <base64>, "mime_type": "application/pdf"}`（`resolution` は付けない）
  - 選ぶ質問: `{"type": "choice", "instructions": 文, "criteria": {<候補の鍵>: <説明>, …}}`
  - 枚数の質問: `{"type": "noul", "instructions": 文}`
- 大きさ: 元の大きさが 画像 20 MB・PDF 50 MB を超えたら呼ばずに `too_large`。
- 返り: `answers[<鍵>]` が、選ぶ質問は `{"type": "choice", "choice": …, "confidence": …}`、枚数は `{"type": "noul", "noul": …}`。入力トークン = `usage.total_input_tokens`。

### 6.3 OpenAI（`gpt-…`。2026-11-21 に公式のガイド「Decisions」と API リファレンスで確認）

- `POST https://api.openai.com/v1/decisions`、ヘッダー `Authorization: Bearer <OPENAI_API_KEY>`・`Content-Type: application/json`。
- 本文: `{"model": 型名, "input": [{"role": "user", "content": [{"type": "input_text", "text": 共通の文}, {"type": "input_image", "image_url": "data:<MIME>;base64,…"}]}], "questions": [<質問>, …]}`
  - 選ぶ質問: `{"type": "choice", "name": <鍵>, "instructions": 文, "choices": [{"value": <候補の鍵>, "description": <説明>}, …]}`
  - 枚数の質問: `{"type": "predicate", "name": "n", "instructions": 文}`
- **PDF は送れない**（このエンドポイントはファイルの入力に対応していない）。PDF は呼ばずに `unsupported_mime`（形 C では要確認のまま。「注」に本数が出る。§7.3）。
- 大きさ: 元の大きさが 20 MB を超えたら呼ばずに `too_large`。
- 返り: `answers` は配列。`name` で質問と結ぶ。選ぶ質問は `{"type": "choice", "choice": …, "confidence": …}`、枚数は `{"type": "predicate", "probability": …}`。入力トークン = `usage.input_tokens`。

### 6.4 返りの確かめ（どちらも同じ関数）

次を全部満たさなければ `失敗:bad_response`（`生の応答` には返りを残す）: 作った質問の全部に答えがある／答えの種類が質問と合う／`choice` が渡した候補の鍵の 1 つ／`confidence`・確率が bool でない有限の数で 0 以上 1 以下。余分な答え・余分な欄は無視する。

**実装の人へ**: 画像の大きさの上限（20 MB）は公式のページに数が無く、控えめに決めた値。API が 400 を返したら `失敗:api_error` として `エラー詳細` に文が残る（やり直さない）。ここに書いた欄の名前と違う返りを見つけたら、推し量って合わせず報告に書く。

## 7. 形 C の計算（`src/compare/forms.py`。API もファイルも触らない）

### 7.1 材料

審判 J = 結果タブに方式 `審判` の行がある型（初めて出た順）。θ = `COMPARE_JUDGE_THRESHOLDS`（score でも同じ環境変数。無ければ既定）。J が 1 つも無ければ C の行は作らない。

### 7.2 明細ごとの判定（J・θ ごと）

D0 = `reconcile(Ib, Tb, OCR の文字)`（R7。今と同じ関数）。「呼ぶ」ファイル = Ib が空でなく D0 に合わない明細がある（形 B と同じ）。

- 呼ばないファイル: 今（両読み）と同じ。
- 呼ぶファイル: D0 で合った明細は自動のまま。合わなかった明細 i は、次を**全部**満たすときだけ自動（ラベルは `一致（審判）`）:
  1. J の方式 `審判` の一番下の行が `成功` で、`明細JSON` が §5.3 の形で読める。
  2. その `base` が、今の Ib の全部の明細の（日付, 金額）と同じ（数も並びも）。
  3. `items` に `i` があり、`a.choice` が Ib[i] の金額の数字と同じで `a.confidence` ≥ θ、`d.choice` が Ib[i] の日付と同じで `d.confidence` ≥ θ。
  4. D0 に「明細数要確認」があるファイルでは、`count.asked` が Ib の明細の数と同じで `count.p` ≥ θ。
- どれかを満たさなければ要確認のまま、ラベルは D0 のまま（J7）。値の比べ方は文字の一致（金額は 10 進の数字、日付は `YYYY-MM-DD`）。
- 性質（テストで確かめる）: C の自動の明細は今（両読み）の自動の明細を含む／θ を上げると自動の明細は増えない／戻りの長さは Ib の長さ。

### 7.3 タブ

「形_<ラベル>」: 今の並び（今 → 読み手ごとの A2・B）の後に、J ごと・θ の小さい順に 1 行ずつ。

- `形` = `C`、`もう1人の読み手` = `<J> ≥<θ を小数 2 桁>`（例 `gemini-decision-1 ≥0.90`）、`もう1人を呼んだ本数` = 呼ぶファイルのうち J の行が `成功` の数。
- 成績（正しく自動・誤って自動・要確認）は今と同じ関数。
- `推定費用USD` = 今（両読み）の費用 ＋ 呼ぶファイルの J の行の `推定費用USD`（行が無い・空は 0。失敗の行に費用があれば足す）。
- `注`: 「審判の行が無いファイル n」（呼ぶファイルなのに J の行が無い）・「審判が失敗したファイル n（<結果ごとの数>）」・「審判に見せた読みと違うファイル n」（§7.2 の 2）。n が 0 のものは書かない。

「形の明細_<ラベル>」: C の行も同じ列で足す。`読み` は `主画像=… ｜ 主文字=… ｜ 審判=<i+1>:<金額の choice>(<確からしさ 2 桁>)/<日付の choice>(<確からしさ 2 桁>), …`（枚数の質問があれば末尾に `枚数=<p 2 桁>`）。`呼んだ` = 呼ぶファイルなら `はい`。

行が増える（156 本 ×（今 1 ＋ 読み手 4 × 2 ＋ 審判 2 × 下限 3）＝ 約 2,300 行）ので、今ある「書く前に行を足す」処理（読み手の仕様 §14.2）が効くことを確かめる。
