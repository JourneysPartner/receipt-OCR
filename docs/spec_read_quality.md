# レシート OCR: 読み取りの質（3.5 flash-lite で正答率を上げる）仕様 1.2

対象は直下の `src/`（Python の Cloud Run Job）。クレカ明細（`クレカ明細自動仕訳/`）には触れない。

## 1. 目的

2026-11-19 の利用者の決定: 型は `gemini-3.5-flash-lite`、その正答率を最大にする。

11-18 の比較（`full-20261118`、156 本）で分かったこと:

- 3.5 flash-lite は「画像から」が「文字から」より良い（日付と金額がともに正しい: 143/149 と 132/149）。
- 今の流れ（文字から＋金額照合）は、誤ったまま自動で転記するものが 15 本ある。
- 「画像から」と「文字から」の日付・金額・件数が一致した 131 本に誤りは 0。食い違った 18 本のうち画像からが正しいのは 12。
- 外し方は、手書きの「¥」を 7 と読む、運賃・切手を非課税と読む、令和の年、店名の省き、の 4 種類が大半。
- 考える量は 0 のまま動いていて、上げた場合は試していない。

この仕様は 3 つを入れる。どれも**切り替えの印を入れるまで本番の動きは変えない**。

1. 指示文の第 2 版（利用者の決まりを書く）
2. 両読みの流れ（画像からを主に読み、文字からと合ったものだけ自動）
3. 比較の道具の直し（1 枚ずつの答え、右に足した列を許す、両読みの集計）

入れた後に比較を流して数字を確かめ、利用者の了解を得てから既定を切り替える（§9）。

## 3. 安全の条件（変えない。すべてテストで確かめる）

- **Q1 既定は今のまま**: `AI_PROMPT_VERSION`・`AI_FLOW` を設定しなければ、型へ送る指示文・呼び出しの順と回数・表へ書く値は今と同じ。指示文の第 1 版は 1 字も変えない（今の文字列と等しいことをテストで固定する）。例外は §6 の補正の決まりだけ（利用者の決定なので常に効く）。
- **Q2 両読みで自動にするのは、合ったものだけ**: 両読みでは、§5.2 で「合った」明細だけを通常の行として書く。それ以外の明細は必ず要確認の行（K 列の頭に `※` の付く行、状態は manual_entry）になる。画像からの明細を黙って捨てない。
- **Q3 行の予約と処理済みの印は今のまま**: `reserve_rows`・`processed_keys`（`<fileId>:<番号>`）・`【済】` を付ける条件（全部が自動のときだけ）は変えない。両読みでの番号は画像からの明細の並び順。
- **Q4 比較モードは今までどおり出納帳・マスター・`【済】` に触れない**（`spec_model_compare.md` §3 の条件はすべて残す）。
- **Q5 「答え」タブ**: P 列（`更新`）より右のマスには書かない・消さない。「メモ」には触れない。「答え_複数」タブは、無いときに見出しだけ作る。中の行は書き換えない・消さない。
- **Q6 例外で止まらない**: 両読みで画像から・文字からのどちらかが例外や 0 件でも、ファイルは要確認の行になり、次のファイルへ進む。

## 4. 指示文の版（`src/ai/prompts.py`）

`AI_PROMPT_VERSION`: `v1`（既定）か `v2`。ほかの値は `load_config` で終了コード 1（文は「`AI_PROMPT_VERSION は 'v1' / 'v2' のいずれか`」）。`AiConfig.prompt_version` に入れる。

- `v1`: 今の `SYSTEM_INSTRUCTION` と、今の 2 つの依頼文（文字から・画像から）をそのまま。
- `v2`: 下の §4.1 を `system_instruction` にする。依頼文は、文字からは「以下はレシート・領収書「<ファイル名>」の OCR テキストです。決まりに従って JSON 配列で返してください。」＋今と同じ区切りと本文、画像からは「これはレシート・領収書「<ファイル名>」の画像または PDF です。画像から直接読み取り、決まりに従って JSON 配列で返してください。」。

`GeminiExtractor` は版に応じて `prompts.py` から取る。比較の「設定」の欄は、版が `v1` 以外のときだけ末尾に `, prompt=<版>` を足す（`v1` のときは今の文字列のまま）。

## 5. 両読みの流れ

`AI_FLOW`: `text_first`（既定。今の流れ）か `dual`。ほかの値は終了コード 1（文は「`AI_FLOW は 'text_first' / 'dual' のいずれか`」）。`AiConfig.flow` に入れる。

### 5.1 `_process_file`（`flow == "dual"` のとき）

今の `text_first` の処理は別の関数に分けて中身を変えない。`dual` は新しい関数にする。

1. ファイル単位のスキップは今と同じ。
2. MIME が画像からに使えない種類（`_RETRY_SUPPORTED_MIMES` に無い）なら、ダウンロードの前に `text_first` の処理へ回す（今と同じ結果）。それ以外は、ダウンロード・OCR を今と同じに行う。ただし OCR が失敗か空でも止めない（OCR の文字は空として進む）。
3. I = `extract_from_file(file)`。T = OCR の文字が空でなければ `extract_receipt_data(ocr, file_name)`、空なら `[]`。それぞれの例外は捕まえて `[]` として扱う。呼ぶのは各 1 回。
4. I も T も空: 今の「抽出失敗」と同じ要確認の行を 1 行（ラベルは今の決め方）。
5. I が空で T がある: T の明細を全部、要確認の行にする（ラベル `※読み取り要確認`）。
6. I がある: `reconcile(I, T, ocr_text)`（§5.2）で明細ごとに決める。`合った` 明細は今の `_write_item` で書く（低信頼の扱いも今のまま）。それ以外は要確認の行にする（候補の値は I の補正後の値。今の `_write_amount_invalid_as_manual` と同じ形で、K 列は「ラベル / 摘要候補」）。
6a. **読み直しのとき**: そのファイルの処理済みの印（`<fileId>:<番号>`、番号 0 以上）が 1 つでもあれば、まだ印の無い番号の明細は、合っていても自動にしない。`※再読取要確認` の行にする（前の回と明細の数や並びが変わった疑いがあり、同じレシートの二重の転記になりうるため。監査 H1）。その回は `【済】` も付かない。
7. 要確認の行の O 列（長い説明）と AI 詳細ログの memo に、両方の読みを残す: `両読み: 画像=<日付>/<金額> ｜ 文字=<日付>/<金額>, …（<理由>）`。合った明細の memo には `両読み=一致`。
8. `【済】` を付ける条件・dry_run（検証）の数え方は今と同じ考え方（合った＝success か low_confidence の予定、それ以外＝manual の予定）。

### 5.2 `reconcile`（`src/processing/reconcile.py`。API もファイルも触らない純粋な関数）

入力は I・T の明細の並びと OCR の文字。出力は I の明細ごとの `(結果, ラベル, 理由)`。

- 日付は `src/compare/normalize.py` の `normalize_date` でそろえ、`YYYY-MM-DD` の実在する日付になったものだけを使う（読めない日付は「空」と同じ扱い）。金額は 1 以上の整数だけ（0 以下は「空」と同じ扱い。監査 M1・L1）。
- I の明細を先頭から順に見て、T のまだ使っていない明細のうち、日付と金額がともに等しい最初のものと組にする（どちらかが空の明細は組にしない）。
- **T の件数が I の件数より多い**: I の全部を `要確認`、ラベル `※明細数要確認`（画像からが 1 枚見落とした疑い）。
- それ以外で、明細ごとに:
  - 組ができ、`validate_amount(金額, OCR の文字)` が `digit_inflation` でない → `合った`
  - 組ができたが `digit_inflation` → `要確認`、`※金額要確認`
  - 組が無く、T の残りに金額だけ等しいものがある → `要確認`、`※日付要確認`
  - 組が無く、T が空（OCR 失敗を含む） → `要確認`、`※読み取り要確認`
  - それ以外 → `要確認`、`※金額要確認`
- 税率・店名・摘要・科目は照らさない（I の値を使う）。

本番と比較（§7.3）は必ずこの同じ関数を使う。

## 7. 比較の道具（`src/compare/`）

### 7.1 「答え」タブの見出し

見出しの検査は A〜P 列（16 列）だけにする。Q 列より右に何があっても止めない・読まない・書かない（Q5）。「答え」の中身を読むときも `A:P` の範囲だけを読む（右の列に同じ見出しがあっても影響を受けない。監査 M5）。A〜P が違えば今までどおり止める。

### 7.2 1 枚ずつの答え（「答え_複数」タブ）

見出し: `fileId` / `ファイル名` / `番号` / `正解_日付` / `正解_金額` / `正解_税率` / `正解_店名` / `メモ`。無ければ collect・score の始めに見出しだけ作る。見出しが違えば止める。

- このタブに `fileId` の行が 1 行以上あるファイルは、その行の並び（番号の順）がそのファイルの答え（レシートの並び）。
- 行が無いファイルは、「答え」の行をレシート 1 枚の答えとして使う（今までどおり。空の欄は答え無し）。
- 「答え」タブの候補・状態・自動の書き込み（`spec_model_compare.md` §9）は今のまま。

### 7.3 結果の行

- 「結果_<ラベル>」の見出しの最後に `明細JSON` を足す: 明細ごとの `{"d": 日付, "a": 金額, "t": 税率, "v": 店名, "s": 摘要, "c": 科目}` の配列（日付・税率は §7 のそろえた値、店名・摘要・科目は補正前の文字）。4 万字を超えるときは空にして「エラー詳細」に `明細JSONが長すぎる` と足す。
- 方式に `両読み` を足す（`COMPARE_METHODS` が `text,image` の両方のときだけ。API は呼ばない）。I・T・OCR の文字から §5.2 の `reconcile` で決め、合った明細と要確認の明細に `RuleCorrector` を当てる。結果は、全部合った＝`自動`、一部＝`一部要確認`、全部だめか I が空＝`要確認`。金額照合の欄に明細ごとのラベル（`一致` か `※…`）。`明細JSON` は補正後の値で、明細ごとに `"r": "自動"` か `"要確認"` を足す。応答ms・トークン・費用は文字からと画像からの合計。
- `現行の流れ` は今のまま残す。
- 見出しの違う古い結果タブ（`明細JSON` が無い）は、続きからも score も「この実行は古い形です。新しいラベルで collect からやり直してください」で止める（何も書かない）。

### 7.4 集計

答えも読みも「レシートの並び」で比べる。ファイルの読みは `明細JSON`、答えは §7.2。

- 読みとして使う行: 文字から・画像からは `成功` の行。`現行の流れ` は今までどおり `自動` の行だけ（`明細JSON` は自動で通った明細）。`両読み` は明細が 1 件以上ある行（`明細JSON` は自動も要確認も含む全部＝表に入る値）。それ以外の行は不正解に数える。

- 並べ方: 金額（空は最後）→ 日付 の順に並べ替えてから、先頭から 1 対 1 で比べる。件数が違えばその欄はすべて不正解。
- 日付・金額・税率・店名の正解率: 分母は、その欄の答えが全部のレシートにあるファイルの数。分子は、全部のレシートでその欄が合うファイルの数（合い方は `spec_model_compare.md` §7）。
- 日付と金額: 両方が全部のレシートで合う数。
- `両読み` と `現行の流れ`（どちらも同じ数え方。自動の明細 = `明細JSON` の `r` が `自動` のもの。行の結果が `一部要手入力`・`一部要確認` でも自動の明細は数える。監査 M3）:
  - `誤って自動`: 自動の明細の中に、答えのどのレシートとも日付・金額が合わないものがある（答えのレシート 1 枚は 1 回だけ使う）。または、結果が `自動` なのに明細の数が答えより少ない（レシートが抜けたまま済みになる。監査 M4）。
  - `正しく自動`: 結果が `自動` で、明細の数が答えと同じで、全部の日付と金額が合う。
  - `要手入力`: それ以外。
  - 3 つは重ならない。
- 集計タブの見出しは今のまま。`両読み` の行を `現行の流れ` の後に足す。
