## 1. 背景

- 転記シート（freee の出納帳の雛形の写し）の「入力用シート」は、3 行目が見出し（B 日付・C 相手科目コード・D 相手勘定科目・F 相手取引先・G 相手税区分・I メモタグ・K 摘要・L 借方・M 貸方・O 取引 ID）。データは 5 行目から。
- **D 列は数式**：`=IF(C5="","",VLOOKUP(C5,$Q$5:$R$49,2,FALSE))`。Q・R 列（5〜49 行目）が科目の一覧（Q＝コードの数、R＝科目名。6 行目は 0「複合」、49 行目の Q は「合計」）。だから **C にコードを数で入れれば D は勝手に出る。D は書かない。**C に文字の `"712"` を入れると VLOOKUP が数の 712 と一致せず、D が `#N/A` になる。
- 今のシステムが書くのは B・F・I・K・M・取引 ID（＋任意の G、マイナスの金額は L）。G は顧客マスターの列対応が任意で、決まった行だけ書く（空を書かない）。C も同じ作りにする。
- 使用用途が空の行は既に【要修正】で止まる（区分 1）ので、記帳される行には用途がある。
- 今ある明細の用途は、80 本・1,987 行で 21 種類（仕入 1654・仕入れ 127・高速代 66・私用 27・ツール代 26・コンサル代 18・ネット代 11・月額利用料 10・スマホ代 9・資材代 9 ほか）。「仕入れ　フィルム」のように品目が付くことがある。顧客ごとに書き方が違う（通信費／スマホ代、高速代／ETC）。

## 4. 言葉の当て方（`38` の純粋な関数）

### 4.1 鍵

`usageWordKey_(value)` ＝ `partnerNameKey_(value)`（`37`。NFKC・大文字・ひらがな→カタカナ・小さい字→大きい字・長音などの記号の統一）の結果から**空白をすべて除いたもの**。用途と辞書の言葉の両方に同じ関数をかける。（例：`ｽﾏﾎ代`→`スマホ代`、`ネット 代`→`ネツト代`（`ネット代` も同じ鍵）、`仕入れ　フィルム`→`仕入レフイルム`。辞書の `仕入` の鍵 `仕入` が先頭で当たる。）

### 4.2 `resolveAccountCode_(purpose, customer, masters, sheetList)`

戻り値：`{status, code, word}`。`status` は `MATCHED`・`NO_MATCH`・`AMBIGUOUS`・`INVALID_ENTRY`・`NOT_IN_SHEET_LIST` のどれか。`code` は `MATCHED` のときだけ整数、ほかは `null`。`word` は当たった辞書の言葉（`NO_MATCH` は `null`）。

1. `key = usageWordKey_(purpose)`。空なら `NO_MATCH`。
2. 候補の辞書行：有効がはっきり `FALSE` でない（読めない値は候補に残す）、鍵が空でない行のうち、
   - 顧客 ID が `customer.customerId` と同じ行（顧客別）、と
   - 顧客 ID が空で、対象が `共通`、または顧客の区分に合う行（`INDIVIDUAL`→`個人だけ`、`CORPORATE`→`法人だけ`）。**対象の値が不正な共通の行も候補に残す**（6 で誤りにするため）。
   - **顧客別の行がある鍵は、その鍵の共通の行をすべて外す**（顧客の言い方が勝つ）。
3. 当たり：候補のうち `key.indexOf(行の鍵) >= 0` の行。位置＝最初の `indexOf`。当たりが無ければ `NO_MATCH`。**当たりに誤りの行（§3.2）が 1 つでもあれば `INVALID_ENTRY`**（4 の優先の絞り込みより前に見る。優先の欄が壊れた私用の行が優先にならず、先頭の言葉が勝って誤った科目が入るのを防ぐ）。
4. 当たりに優先（E が `TRUE`）の行があれば、優先の行だけを残す。
5. 位置がいちばん小さい行を残し、その中で鍵がいちばん長い行を残す（＝決勝の行）。
6. （1.1 で 3 へ移した。決勝の行は誤りの行を含まない。）
7. 決勝の行のコードが 2 種類以上なら `AMBIGUOUS`。
8. コード 1 つに決まったら、科目一覧のその科目の対象が顧客の区分に合うことを確かめる（合わなければ `INVALID_ENTRY`。§3.2 の検査と重なるが、二重に守る）。
9. `sheetList`（§6）にそのコードが無い、または `normalizeMerchant(転記シートの科目名) !== normalizeMerchant(科目一覧の科目名)` なら `NOT_IN_SHEET_LIST`。
10. ここまで通れば `MATCHED`。

1.1 で足す例（ac 1）：私用の行の優先の欄が `はい` のとき `仕入 私用` → `INVALID_ENTRY`（1.0 では 712 が入った）／顧客別の `ツール代` の有効の欄が `○` で共通の `ツール代` もあるとき → `INVALID_ENTRY`（1.0 では共通のコードが入った）／`仕入` は正しく `フイルム` の行が科目一覧に無いコードのとき `仕入れ フィルム` → `INVALID_ENTRY`。

例（テスト ac 1 で固定する）：`仕入れ　フィルム`→712／`仕入れ スマホケース`→712（`スマホ` は位置 3 なので負ける）／`スマホ代`→843／`高速代`→842／`私用 仕入`→個人 294・法人 362（優先）／`仕入 私用分`→個人 294（優先はどこにあっても勝つ）／`月額利用料`→共通だけなら `NO_MATCH`、顧客別の行があればそのコード。

## 12. 運用関数（`97`。既定は見るだけ）

### 12.1 `opsSeedAccountMasters(apply)`

`39` の種（§13）を 2 枚のシートへ入れる。

- 見るだけ（既定）：2 枚を読み、`{accounts: {toAdd, existing, differs}, words: {toAdd, existing, differs}, problems, applied: false}` を返す。
  - 科目：同じコードの行があれば `existing`（名前と対象も同じ）か `differs`（違う。今の値と種の値を並べる）。無ければ `toAdd`。
