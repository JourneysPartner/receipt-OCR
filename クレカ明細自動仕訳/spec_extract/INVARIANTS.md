# 3. 不変条件

本章は、モジュールをまたいで常に成り立たなければならない規則を列挙する。第4章の各モジュール契約は本章の番号を参照する。**実装のレビューと受入試験は、本章を項目リストとして使用する。**

| # | 不変条件 | 破った場合に起きること | 主な参照モジュール |
|---|---|---|---|
| INV-01 | **シート値を変更した操作は、必ず同一の操作の中で取引ログの予定値（S〜W列）と読取確認値（X〜AB列）を同時に更新する。** シートだけ、または予定値だけを更新して終わってはならない | 読取確認値が空欄または旧値のまま残り、次回の整合性チェック（検査3）が解決済み取引をすべて「手動変更」と誤検知して処理開始前に必ず停止する | 4.23／4.26／4.29 |
| INV-02 | **シート由来の真偽値は正規化してから判定する。`=== true`で比較しない。** 読取時に行オブジェクトへ詰める段階で`toBool()`を通し、以後は正規化済みの値だけを扱う | 値が文字列`'TRUE'`になり、辞書競合フラグが偽に落ちて競合が自動確定され、有効フラグが偽に落ちて重複判定が常に「重複なし」になる。いずれも例外を出さず静かに壊れる | 4.18／4.21／4.32／4.38 |
| INV-03 | **取引ログ・恒久取引インデックスの単一取得は「取引ID完全値かつ有効=TRUE」を一意キーとする。** 有効=TRUEの行が2行以上あれば自動修復せず整合性エラーで停止する | 取消し→再処理で同一取引IDのsupersede済み行を拾い、`CANCELED`からの遷移が空集合であるため仕様17.3の「未処理へ戻して再処理」が常に失敗する | 4.32／4.24／4.21 |
| INV-04 | **容量測定・可用性測定は必須ログの内容を変更してはならない。** 追記可否の実測は専用の容量プローブシート（2.1.17）のA1セルへの書込で行い、行の増減を伴わない | 処理ログへダミー行を追記して削除する方式では、追記と削除の間に別実行が本物のログ行を追記した場合に実ログ行を削除する。1行の消失が二重転記に直結する | 4.37 |

| INV-06 | **空き行判定・テンプレート行拡張・行予約は、単一のLockService排他区間の中で行う。** 排他区間内で予約対象行が空であることを読み直して確認してから予約する | 判定がロック外にあると、並行処理する2ファイルが同じ空き行集合を得て後勝ちで上書きし、先の取引は行を失ったまま`COMMITTED`になり得る | 4.23／7.2 |
| INV-07 | **提出時点の値から計算するハッシュ（明細内容ハッシュ・取引同一性ハッシュ）は不変であり、修正で上書きしない。** 修正後のハッシュが必要な場合は別列（処理ログN列）へ記録し、重複判定・修正版候補照合・部分一致警告には提出時点の値だけを使う | 日付・金額修正で提出時点ハッシュが置き換わると、顧客が同一の元ファイルを再提出しても一致せず全件が再取込される | 4.26／4.21／4.31／4.32 |
| INV-08 | **転記先シートの読取は取引ごとに行わない。** ヘッダー定義範囲を値と数式の2通りで一括取得してインデックスを構築し、以後の照合はメモリ上で行う。整合性チェック・取込後変更検出・部分失敗回復・空き行判定は同一のインデックスを共有する | 取引1件ごとに読むと5,000取引で5,000回の読取となり、実行時間上限とクォータの両方を超える | 4.25／4.24／4.28／4.23 |
| INV-09 | **外部API呼出の計上は例外を投げない。** 計上関数は使用量の加算と接近フラグの設定だけを行い、離脱の判定は呼出元が**取引境界またはバッチ境界**で行う | 計上時に例外を投げると、値の書込に成功した直後・読取確認と取引状態更新の前に実行が終わり、取引が`WRITING`のまま値だけシートに入った状態になる | 4.37／4.23 |

| INV-13 | **バージョンの異なるハッシュ・取引IDを直接一致比較しない。** 比較の前に`hashVersion`／`transactionIdVersion`の一致を確認し、不一致は「比較不能」として扱う（一致とも不一致とも判定しない） | 生成規則の変更後に旧記録と新記録を比較し、偽の一致または偽の不一致で二重転記または誤停止を起こす | 4.21／4.20 |
| INV-14 | **事前検証がすべて完了するまで転記先へ1セルも書き込まない。** 事前検証結果の区分判定は**区分2 → 区分1 → 区分3** の順に評価する | 途中行まで書いた後に不備を発見する実装になる。また区分1を先に評価すると、管理者側の不備が顧客への差戻しに隠れて是正されない | 4.14／4.22 |
| INV-15 | **書込後の読取確認を経ずに`COMMITTED`にしない。** 読取・比較の正規化規則は5.5の単一の表に従い、書込・読取確認・整合性チェック・取込時点ハッシュのすべてが同じ規則を使う | 書込要求の成功応答だけで確定すると部分書込を検出できない。正規化規則が箇所ごとに異なると、日付列が恒常的に不一致となり全取引が停止する | 4.23／4.24／4.28 |

| INV-17 | **「全明細が解決済み」の判定は要確認の件数ではなく、取引ログの状態で行う。** ファイルに属する`有効=TRUE`の全取引が「`transactionStatus`が`COMMITTED`／`CANCELED`／`DELETED_ACCEPTED`のいずれか」であり、**かつ`transactionStatus`が`COMMITTED`である取引に限り`partnerResolutionStatus`が`UNRESOLVED`でない**ことをもって解決済みとする。**加えて、当該ファイルに`有効=TRUE`の取引が1件も存在しない場合は、処理ログAN列（0件確認）がTRUEのときに限り`COMPLETED`と判定してよい** | 前段の限定がないと、取引先不明の1件を「対象外」で解決した取引が`CANCELED`かつ`UNRESOLVED`となり、ファイルが永久に`REVIEW_WAIT`から抜けられない。後段がないと、区分2で停止して取引を1行も登録していないファイルが空集合に対して真となり【済】になる | 4.9／4.26／4.28 |
