## 仕様書 Ver.2.0

作成日：2026年8月23日  
最終改訂日：2026年8月23日  
対象：Google Drive／Googleスプレッドシート／Google Apps Script  
文書状態：レビュー改訂中

# 1. 文書の目的

本書は、顧客がGoogle Driveへ提出するクレジットカード利用明細を読み取り、既存のfreeeクレカ出納帳へ安全に転記し、カード会社固有の利用店名をfreee取引先へ正規化するシステムの要件を定義する。

本書はVer.1.0のレビュー結果および運用判断を反映し、特に次の事項を明確化したものである。

- 途中停止・再実行時にも二重転記しないこと
- 要確認明細と転記先行を内部取引IDで一意に結び付けること
- 元利用店名とfreee取引先の書込先を分離すること
- ファイルの処理状態、修正、取消し、復元を追跡できること
- 共通辞書・顧客別辞書・既存取引先一覧の優先順位を統一すること
- AIをVer.1.0の必須要件から外し、後続フェーズの候補提示機能とすること

# 2. システム目的と適用範囲

## 2.1 目的

現在、人手で行っている次の作業を自動化する。

1. 顧客別Google Driveフォルダから未処理明細を検索する。
2. CSV・XLSXファイルのカード形式を判定する。
3. 利用日、金額、利用店名、使用用途を抽出する。
4. 顧客別のfreeeクレカ出納帳「入力用シート」へ転記する。
5. 利用店名からfreee取引先を判定する。
6. 判断できない箇所だけを人間の確認対象とする。
7. 人間の確定結果を顧客別辞書へ蓄積し、次回以降に再利用する。
8. 処理結果、変更、取消し、復元を後から追跡可能にする。

## 2.2 自動化範囲

自動化範囲は次のとおりとする。

```text
顧客提出ファイル
  ↓
明細抽出・検証
  ↓
取引先判定
  ↓
顧客別「入力用シート」への転記
  ↓
既存のfreee取込用変換処理
```

freeeへの実際のインポート操作は現行運用を維持する。Ver.1.0ではfreee APIによる直接登録・修正を行わない。

## 2.3 初期対象外

- freee APIによる直接仕訳登録
- 勘定科目・税区分・品目・部門のAI判定
- PDF・画像明細のOCR
- 銀行明細、電子マネー明細
- インボイス登録番号検索
- Googleスプレッドシート形式の明細
- `.xls`、`.xlsm`等の未定義形式

# 3. 最重要原則

優先順位は次のとおりとする。

1. 誤った自動記帳をしない。
2. 二重転記を発生させない。
3. 既存約2,900件の取引先資産を最大限利用する。
4. 人間の修正結果を次回以降に再利用する。
5. カード会社の仕様変更に対応しやすくする。
6. 既存freee取込用スプレッドシートを壊さない。
7. AIへ依存しすぎない。
8. 処理結果と変更履歴を後から追跡できるようにする。

本書で「必須」「する」「しない」と記載した事項は受入必須要件とする。「原則」は、例外条件と記録方法が本書またはカード形式定義に明示されている場合だけ外せる。「検討する」は初期リリースの受入対象外とする。

# 4. システム構成

## 4.1 利用サービス

- Google Drive（マイドライブおよび共有ドライブ）
- Googleスプレッドシート
- Google Apps Script
- 必要に応じてGoogle Drive API
- 現在使用中のfreeeクレカ出納帳
- マスタースプレッドシート

## 4.2 マスタースプレッドシート

最低限、次のシートを設ける。

| シート名 | 役割 |
|---|---|
| 顧客マスター | 顧客、Driveフォルダ、転記先、権限、処理可否を管理 |
| カード形式マスター | 単純な表形式の判定・列定義・バージョンを管理 |
| 使用用途補完マスター | ファイル名キーワードから使用用途を補完 |
| 共通取引先一覧 | 全顧客共通のfreee取引先正本 |
| 共通取引先辞書 | 共通の元表記・正規化表記・承認済みパターンを管理 |
| 顧客別取引先辞書 | 顧客固有の取引先変換を管理 |
| 要確認 | 取引先、データ不正、重複・変更候補等を管理 |
| クレカ処理ログ | 実行・ファイル単位の処理結果を管理 |
| クレカ取引ログ | 取引単位の状態、元値、転記値、転記先を管理 |
| 監査ログ | 変更・承認・取消し・復元・権限操作を追跡 |
| 同期ログ | 共通取引先一覧から顧客別一覧への同期状態を管理 |
| freee取込管理 | freee取込済みの取引ID、日時、実行者を管理 |

クレカ取引ログは任意ではなく、二重転記防止のための必須シートとする。

# 5. 顧客管理

顧客マスターは最低限、次の項目を保持する。

| 項目 | 内容 |
|---|---|
| 顧客ID | 変更されない内部識別ID |
| 顧客名 | 表示用名称 |
| クレカ処理対象 | TRUE／FALSE |
| 明細フォルダID・URL | 検索対象Driveフォルダ |
| 転記先スプレッドシートID・URL | 顧客別freeeクレカ出納帳 |
| 転記先シート名 | 原則「入力用シート」 |
| 取引先一覧シート名 | 同期先の取引先一覧 |
| 入力列設定 | B・F・I・K・Mおよび内部取引ID列 |
| シート構成バージョン | 転記前検証に使用 |
| 確認担当者 | 要確認を処理できるユーザー |
| システム管理者 | 管理操作を行えるユーザー |
| 備考 | 任意 |

顧客名ではなく顧客IDを処理キーとする。登録時にDriveの読取、ファイル名変更、転記先書込の権限を検証する。

# 6. 対象ファイルと検索

## 6.1 対応形式

- `.csv`
- `.xlsx`

CSVはUTF-8（BOM有無）およびShift_JISを自動判定する。判定不能または文字化けの疑いがある場合は取り込まない。引用符内のカンマ・改行等はCSV規則に従って解析する。

XLSXは必要に応じて一時的にGoogleスプレッドシートへ変換して読み取る。一時ファイルは処理終了後に削除し、元ファイルの内容は変更しない。

## 6.2 検索範囲

顧客マスターに登録されたフォルダ配下を再帰的に検索する。マイドライブと共有ドライブの両方に対応する。Driveへのアップロード日時が古いファイルから処理し、同時刻の場合はファイル名、ファイルIDの順で固定する。

最終更新から10分以上変更がないファイルのみ処理する。10分未満のファイルはエラーとせず、次回まで待機する。

## 6.3 処理前プレビュー

全件処理の書込前に、次を表示する。

- 対象顧客数
- 対象ファイル一覧
- 推定明細数
- 待機・警告・要修正候補
- 重複ファイル候補

担当者はファイル単位で今回の処理対象から外せる。外したファイルは未処理のまま残す。

# 7. ファイル状態管理

## 7.1 状態とファイル名

| 状態 | ファイル名・管理 |
|---|---|
| 未処理 | 接頭辞なし |
| 処理中 | `【処理中】元ファイル名` |
| 要修正 | `【要修正】元ファイル名` |
| 完了 | `【済】元ファイル名` |
| 取消済 | `【取消済】元ファイル名` |
| 対象外 | `【対象外】元ファイル名` |

ファイル名は人が見分けるための表示であり、処理状態の正本は内部ログとする。名称変更に失敗しても、内部ログが処理済みであれば再転記しない。

【済】は「本システムによる明細抽出・転記・要確認解決が完了した」ことを表し、freeeへの実インポート完了を表さない。freee取込済みかどうかは16章の取込管理を正本とする。

## 7.2 状態遷移

```text
未処理
  ↓ 読取開始
【処理中】
  ├─ 全明細が解決済み → 【済】
  ├─ 取引先・データ要確認あり → 【処理中】を維持
  ├─ 使用用途不足・顧客修正要 → 【要修正】
  ├─ 担当者が対象外と確定 → 【対象外】
  └─ 取消操作 → 未処理へ戻す／【取消済】を選択
```

未判定取引が残る間は【処理中】とし、全件解決後に【済】へ変更する。【処理中】は通常の未処理検索から除外する。

ファイル名の接頭辞とは別に、内部ログでは少なくとも次の内部状態を保持する。

| 内部状態 | 意味 | ファイル名接頭辞 |
|---|---|---|
| `DISCOVERED` | 未処理として検出済み | なし |
| `VALIDATING` | 読取・事前検証中 | 【処理中】 |
| `WRITING` | 転記中 | 【処理中】 |
| `REVIEW_WAIT` | 要確認または形式登録待ち | 【処理中】 |
| `CUSTOMER_FIX_REQUIRED` | 顧客による元ファイル修正待ち | 【要修正】 |
| `COMPLETED` | 全明細の処理が完了 | 【済】 |
| `CANCELED` | 取消済み | 【取消済】 |
| `EXCLUDED` | 対象外として確定 | 【対象外】 |
| `FAILED` | システムエラーで停止 | 原則【処理中】 |

処理リースとハートビートを必要とするのは`VALIDATING`および`WRITING`だけとする。`VALIDATING`・`WRITING`以外の内部状態へ遷移する際は処理リースを解放し、以降はハートビート途絶を中断と判定しない。`REVIEW_WAIT`を異常終了と判定して自動再開してはならない。通常検索は接頭辞ではなく内部状態を基準とし、再開・要確認メニューでは`REVIEW_WAIT`および`FAILED`を明示的に検索できるようにする。

主要な内部状態からの復帰・終端は次のとおりとする。

- `FAILED`：管理者の指示で`VALIDATING`へ戻し、取引ID単位で続きから再検証・再開する。
- `CUSTOMER_FIX_REQUIRED`：顧客修正後の再検査で`VALIDATING`へ戻す。
- `CANCELED`：管理者が再処理を選んだ場合に`DISCOVERED`へ戻し、未処理として再検出させる。
- `EXCLUDED`：オーナー管理者が対象外を解除した場合に`DISCOVERED`へ戻す。
- `COMPLETED`：通常の終端状態であり、以降の再処理は取消し・復元・再取込の明示操作によってのみ行う。

## 7.3 形式不明

形式不明ファイルもファイル名は【処理中】のままとする。システム上で次を明示する。

```text
対応者：当社システム管理者
理由：カード明細形式を判定できない
必要な対応：サンプルとして新しい明細形式を登録する
```

形式不明は内部状態を`REVIEW_WAIT`とし、処理リースを解放する。形式登録後、管理者の再検査指示で`VALIDATING`へ戻す。

## 7.4 状態更新とファイル名変更

内部状態を先に確定してログへ保存し、その後にファイル名を変更する。名称変更に失敗した場合は内部状態を巻き戻さず、名称変更失敗として再試行対象にする。同じ接頭辞を重ねて付与せず、元ファイル名は初回検出時の値を不変で保持する。

# 8. カード形式判定とパーサー

## 8.1 判定順序

1. 特徴的なヘッダー
2. ファイル内シグネチャ
3. 既知の列構造・データ型
4. カード形式マスター

複数形式が候補となった場合は自動処理せず要確認とする。

## 8.2 XLSXの複数シート

明細形式を判定できるシートが1つだけの場合に処理する。複数見つかった場合は重複・集計シート混入の可能性があるため要確認とする。取引IDとログにはシート名を含める。

## 8.3 新しい形式の登録

単純な表形式は、システム管理者がサンプルを選び、ヘッダー行、日付列、店名列、金額列、使用用途列、除外条件をカード形式マスターへ登録できるようにする。

登録直後は「下書き」とし、抽出プレビューで全明細、除外行、件数、合計をシステム管理者が確認する。下書きの有効化はオーナー管理者の承認後に限り行う。複雑な複数表、特殊な終了条件等を持つ形式は専用パーサーを追加する。

## 8.4 初期対応カード

### Amazon Mastercard系

| 項目 | 元ファイル |
|---|---|
| 日付 | A列 |
| 利用店名 | B列 |
| 金額 | C列 |
| 使用用途 | G列 |

1行目付近の「Amazonマスター」等、G列付近の「使用用途」、A～C列のデータ構造を使用して判定する。実取引は原則2行目以降とし、有効日付等で検証する。

### dカード系

| 項目 | 元ファイル |
|---|---|
| 日付 | D列 |
| 利用店名 | E列 |
| 金額 | F列 |
| 使用用途 | K列 |

ヘッダーは原則2行目。「ご利用年月日」「利用店名」「利用金額」「使用用途」で判定する。ご入金、集計、合計、キャッシング見出し、空行等を除外する。返品の負数は維持する。

### セゾンカード系

| 項目 | 元ファイル |
|---|---|
| 日付 | A列 |
| 利用店名 | B列 |
| 金額 | F列 |
| 使用用途 | H列 |

「カード名称」「セゾン」「利用日」「ご利用店名及び商品名」「利用金額」「使用用途」で判定する。ヘッダーは原則5行目、実取引は原則7行目以降だが、有効日付等で検証する。

### 楽天カード系

| 項目 | 元ファイル |
|---|---|
| 日付 | A列 |
| 利用店名 | B列 |
| 金額 | E列 |
| 使用用途 | K列 |

「利用日」「利用店名・商品名」「利用金額」「使用用途」で判定する。ヘッダーは原則1行目、明細は2行目以降とする。

# 9. 明細抽出・検証

## 9.1 共通取引データ

パーサーの出力を次の共通構造へ統一する。

```javascript
{
  customerId: "C001",
  fileId: "...",
  fileNameOriginal: "...",
  fileRevision: "...",
  sourceSheet: "Sheet1",
  sourceRow: 12,
  cardType: "rakuten",
  date: Date,
  merchantOriginal: "ﾄﾞﾝｷﾎｰﾃﾅｶﾞｵｶｶﾜｻｷ",
  amountBillingJpy: 5015,
  purpose: "仕入",
  currencyOriginal: "USD",
  amountOriginal: 35.00,
  dateInferenceSource: null,
  dateTimezone: "Asia/Tokyo",
  purposeInferred: false,
  purposeInferenceRuleId: null
}
```

日付の解釈・シリアル値変換・年補完はすべてタイムゾーン`Asia/Tokyo`を基準に行い、`dateTimezone`へ明示する。`purposeInferred`は使用用途をファイル名補完で補ったかを示し、補完した場合は適用した補完ルールを`purposeInferenceRuleId`に記録する（補完していない場合は`false`／`null`とする）。

## 9.2 有効明細の基本条件

カード形式固有ルールを優先し、原則として日付、金額、利用店名の構造から取引候補を判断する。単純に最終行まで読み取らない。

日付または金額がある行は取引候補として検証する。日付・金額がない見出し、空行等は使用用途が空欄でも問題としない。

## 9.3 日付

- B列には実際のカード利用日を記載する。
- 処理日、売上確定日、支払日は利用日がない形式でのみ代替候補とする。
- Excelシリアル値、文字列等を正しい日付型へ変換する。
- 年を含まない日付は、ファイル名、請求年月、ヘッダーから年が一意に決まる場合だけ補完する。
- 補完根拠をログへ保存し、曖昧な場合は要確認とする。

## 9.4 金額

- M列にはカード会社が最終的に請求する日本円金額を数値で記載する。
- 正数、負数、カンマ付き数値、Excel数値を許容する。
- 返品等の負数は符号を維持する。
- 現地通貨額、通貨コード、換算レートは補足情報として取引ログへ保存する。
- 0円明細は行を確保して要確認とし、担当者が計上または対象外を判断する。

## 9.5 利用店名

K列には顧客提出ファイルに記載された元利用店名をそのまま記載する。正規化後の名称やfreee取引先名で置き換えない。

日付と金額があるにもかかわらず利用店名が空欄の場合は原則【要修正】とする。カード形式固有ルールで正当な取引と確認できる場合だけ、K列・F列を空欄にして要確認として扱う。

## 9.6 使用用途

使用用途は顧客入力値を原則そのままI列へ記載し、自動修正しない。

有効明細行では使用用途を必須とする。ただし、使用用途補完マスターの「ファイル名キーワード → 使用用途」に一意に一致した場合、空欄行だけを補完する。初期ルールは次のとおりとする。

| ファイル名キーワード | 補完する使用用途 |
|---|---|
| 仕入 | 仕入れ |
| 仕入れ | 仕入れ |

一致した複数ルールがすべて同じ使用用途を返す場合は一意とみなして補完できる。異なる使用用途を返すルールが複数一致した場合は補完しない。したがって、ファイル名に「仕入れ」が含まれ、「仕入」と「仕入れ」の両ルールへ一致しても、両方が「仕入れ」を返すため補完できる。

補完できない空欄が1件でもあればファイル全体を転記せず【要修正】とし、顧客が元ファイルを修正してから再検査する。

## 9.7 件数・合計照合

元ファイルに利用件数、合計金額、請求額等がある場合、形式別の照合式で抽出結果と比較する。不一致の場合は【処理中】のまま要確認とする。手数料、前月残高、返品等により単純一致しない形式は専用式を定義する。

有効明細が0件の場合は自動で【済】にしない。担当者が「0件で正しい」と確認した場合だけ完了とする。

## 9.8 ファイル単位の事前検証と書込開始条件

全候補行の解析と事前検証を完了してから、入力用シートへの初回書込みを開始する。途中行まで書いた後で使用用途不足等を発見する実装にしてはならない。

事前検証結果は次の3区分とする。

1. **ファイル全体を無書込で差し戻す**：補完不能な使用用途不足、原則としての利用店名不足など、顧客が元ファイルを修正すべき不備。内部状態は`CUSTOMER_FIX_REQUIRED`とする。
2. **ファイル全体を無書込で管理者確認にする**：形式不明、複数形式候補、複数の認識対象シート、転記先形式不一致など、構造または管理設定の不備。内部状態は`REVIEW_WAIT`とする。
3. **取引行を確保して明細単位で確認する**：形式自体は確定しているが、日付・金額の読取不正、0円、またはカード形式固有ルール上は正当な利用店名空欄がある場合。10.3に従い、判明項目と内部取引IDを書き、該当項目だけを要確認とする。

書込開始後に障害が発生した場合は、11章の取引単位ログと冪等性規則に従って再開する。

# 10. 転記先仕様

## 10.1 書込列

| 項目 | 入力用シート |
|---|---|
| 利用日 | B列 |
| freee取引先 | F列 |
| 使用用途 | I列 |
| 元利用店名 | K列 |
| 日本円請求額 | M列 |
| 内部取引ID | 未使用の非表示・保護列 |

内部取引ID列は、既存数式およびfreee取込範囲に影響しない列を顧客ごとに設定する。システムだけが変更できるよう保護する。

## 10.2 F列の既存数式

既存F列には取引先判定数式が入っている。システム取込行についてはF列の数式を消し、次の固定値へ置き換える。

- 自動判定済み：判定したfreee取引先名
- 要確認：空欄
- 取引先なしで確定：空欄だが内部ステータスは解決済み

他の既存行の数式は変更しない。テンプレート行を複製する場合も、システム取込行ではF列数式をコピーしない。

## 10.3 要確認行の初回転記

取引先のみ要確認の場合も、初回処理でB・I・K・M列と内部取引IDを転記し、F列だけ空欄にする。要確認確定時は新しい行を追加せず、内部取引IDで該当行を検索して同じ行のF列を更新する。

日付・金額が不正な場合も元の位置に行を確保し、判明している項目と内部取引IDを記載する。不正項目は空欄とし、要確認シートで修正後に同じ行を更新する。

## 10.4 空き行判定

未使用F列に数式が存在し、日付不正行ではB列が空欄となるため、B列または`getLastRow()`だけに依存しない。

次のいずれかに該当する行は使用中と判定する。

- 内部取引IDがある。
- B・I・K・M列のいずれかに値がある。
- 既存手入力行として識別できる。

未使用行のF列数式だけは使用中判定の根拠にしない。

## 10.5 数式・書式の拡張

入力可能なテンプレート行を使い切った場合、検証済みの直前行から数式、書式、入力規則だけを複製する。B・F・I・K・M列および内部取引ID列の値はコピーしない。コピー元の構成が不正な場合は処理を停止する。

## 10.6 転記先構成検証

書込前にシート名、ヘッダー、B・F・I・K・M列、内部取引ID列、必要数式、保護範囲を検証する。不一致の場合は書込みを停止し、「転記先形式不一致」としてログへ記録する。

# 11. 内部取引IDと冪等性

## 11.1 取引ID

基本要素は次のとおりとする。

```text
顧客ID + DriveファイルID + 元シート名 + 元ファイル行番号
```

これをSHA-256でハッシュ化し、`TX_...`形式の内部取引IDを生成する。

取引IDの再現性を保つため、次を厳守する。

- DriveファイルIDは顧客が提出した元ファイルのIDとし、XLSXを一時的にGoogleスプレッドシートへ変換した作業用ファイルのIDは用いない。変換用ファイルは再変換のたびにIDが変わり得るため、これを用いると同一取引が再実行時に別IDとなり二重転記の原因になる。
- 元ファイル行番号は、変換前の元シートにおける再現可能な物理行番号（ヘッダー行・空行を含む絶対行）とし、解析時に見出し・空行等を除外しても値が変わらないようにする。同一性照合の出現順（12.1）とは別概念として扱う。
- 上記4要素の連結は、12.1の各ハッシュと同じく各要素の長さ情報を区切りとする決定的な直列化で行い、要素内にファイルIDやシート名の区切り文字が含まれても連結が曖昧にならないようにする。
- 取引ID生成規則にもバージョンを付けてログへ保存し、異なるバージョンで生成したIDを直接一致比較しない。生成規則を変更する場合は、既登録取引のIDと不整合を起こして二重転記を招かないよう、別途移行手順を定める。取引ID生成規則は12.1の各ハッシュと直列化規則（各要素の長さ区切り）を共有するため、直列化規則自体を変更する場合は取引ID生成規則バージョンと12.1の`hashVersion`を同時に更新し、双方のバージョンをログへ保存する。

ハッシュのSHA-256完全値は取引ログへ保存する。入力用シートや画面に用いる表示IDは、衝突が起きない十分な長さへ短縮してよい（短縮文字数は固定せず、運用規模に応じて設定する）。ただし、同一顧客・同一転記先の範囲で表示IDが一致するのに完全値が異なる取引を検出した場合は、表示ID衝突エラーとして処理を停止し、要確認とする。突合や冪等判定は短縮した表示IDではなく完全値を用いて行う。

## 11.2 書込前登録

転記前にクレカ取引ログへ取引ID、元値、予定転記値および`PREPARED`状態を登録する。転記後に転記先スプレッドシートID・シート名・行番号・読取確認値を保存し、`COMMITTED`へ更新する。再実行時は入力用シートの保護された取引IDと取引ログを突合し、転記済み行を追記しない。

取引状態は少なくとも`PREPARED`、`WRITING`、`COMMITTED`、`REVIEW_REQUIRED`、`CANCELED`、`DELETED_ACCEPTED`を持つ。状態変更は更新前状態を条件にした比較更新として扱い、想定外の状態から上書きしない。

各取引状態の遷移と契機は次のとおりとし、いずれも更新前状態を条件とした比較更新で行う。

| 遷移 | 契機 |
|---|---|
| （なし）→ `PREPARED` | 11.2の書込前登録 |
| `PREPARED` → `WRITING` | 転記先行の予約・書込みを開始する時点（19.1）。行予約で内部取引IDだけを書いた状態を含む |
| `WRITING`（再開時は`PREPARED`を含む）→ `COMMITTED` | 11.4の読取確認を終えた解決済み取引 |
| `WRITING`（再開時は`PREPARED`を含む）→ `REVIEW_REQUIRED` | 要確認項目を残す取引（10.3・11.3） |
| `REVIEW_REQUIRED` → `COMMITTED` | 要確認が15章で取引として確定し、同じ取引IDの行を更新した時点 |
| `COMMITTED`・`REVIEW_REQUIRED` → `CANCELED` | 17.3の取消し |
| `COMMITTED` → `DELETED_ACCEPTED` | 17.1で復元せず削除として確定した場合 |

`COMMITTED`から`PREPARED`等への直接復帰は行わない。確定済み取引の再処理は17章の取消し・復元・再取込の明示操作を経る。要確認を対象外として解決する等、上表以外の終端は15章・17章の規定に従う。

## 11.3 途中失敗

一部書込後にログ、名称変更、通知等が失敗しても、再実行は取引ID単位で続きから行う。ファイル単位の追記を最初から繰り返さない。

Google Sheetsとログ用スプレッドシートをまたぐ単一トランザクションは存在しないため、再実行時は次の順で回復する。

1. `PREPARED`または`WRITING`の取引IDを抽出する。
2. 転記先の保護された内部取引ID列を検索する。
3. 取引IDが1行だけ存在し、B・F・I・K・M列が予定値と一致する場合は追記せず、予定した最終状態（解決済みなら`COMMITTED`、要確認を残す取引なら`REVIEW_REQUIRED`）へ補正する。
4. 取引IDが1行だけ存在するが、B・F・I・K・M列がまだ予定値と一致せず（行予約時に取引IDだけを書いた状態や書込み途中の状態を含む）、当該取引が一度も`COMMITTED`になっていない場合は、その予約済みの同じ行へ予定値を書き込み、11.4の読取確認を経て3と同じ最終状態へ更新する。新しい行を追加しない。
5. 取引IDが存在しない場合だけ、現在も有効な処理リースを確認して空き行へ書く。
6. 同じ取引IDが複数行にある場合、または当該取引が既に`COMMITTED`であるのに現在値が保存値・予定値と異なる場合は、自動修復せず整合性エラーとして停止する（後者は手動変更の可能性があるため17.2に従う）。

## 11.4 書込単位と読取確認

1取引のB・F・I・K・M列と内部取引ID列は、可能な限り1回の`Range.setValues()`またはSheets APIの単一バッチ要求で書く。書込み直後に内部取引IDと対象列を再読込し、予定値との一致を確認してから`COMMITTED`にする。書込要求の成功応答だけで確定扱いにしない。

複数取引をまとめて書く場合も各取引の結果を個別に照合し、未確認取引を一括で`COMMITTED`にしない。ログ状態更新に失敗した場合は11.3の回復対象として残す。

## 11.5 元ファイル修正と取引ID

`CUSTOMER_FIX_REQUIRED`では入力用シートへ行を書いていないため、顧客が元ファイルを修正して再検査した時点のシート名・行番号から取引IDを生成する。すでに取引行を確保したファイルが同じDriveファイルIDのまま変更された場合は、取引IDを自動再生成せず12.5の「処理済みファイル変更」として扱う。行追加・削除で元行番号がずれた場合も担当者確認なしに既存取引へ対応付けない。

# 12. ファイル・取引の重複防止

## 12.1 保存する識別情報

- DriveファイルID
- 更新日時またはリビジョン
- 元ファイル名
- ファイルバイナリハッシュ
- 明細内容ハッシュ
- 取引同一性ハッシュ

明細内容ハッシュは解析後の取引一式から生成し、XLSXを保存し直してバイナリが変わった場合にも論理的な重複を検出する。

各ハッシュは次の規則で生成する。

- ファイルバイナリハッシュ：アップロードされたファイルのバイト列そのものをSHA-256で計算する。
- 明細内容ハッシュ：カード形式バージョン、元シート名、取引順、利用日、日本円請求額、元利用店名、使用用途を、型と文字列長を含む決定的な形式で直列化し、SHA-256で計算する。表示形式、空白セルの数、XLSXの保存日時等は含めない。
- 取引同一性ハッシュ：本節末尾の定義に従い、使用用途を含めずに計算する。

日付は`YYYY-MM-DD`、金額は整数円の10進表記、文字列はUnicodeコードポイントを保持したUTF-8として直列化する。ハッシュ仕様自体にバージョンを付け、ログへ`hashVersion`を保存する。異なる`hashVersion`の値を直接一致比較しない。

取引同一性ハッシュは、顧客ID・利用日・日本円請求額・正規化前の元利用店名を、各要素の長さ情報を区切りとして連結した文字列からSHA-256で生成する。出現順は含めない。長さ区切りを用いるのは、要素の内容に区切り文字が含まれても連結が曖昧にならないようにするためである。

同日・同額・同店舗の正当な複数取引や、別ファイルに現れる同一取引は、同じ取引同一性ハッシュを持ち得る。したがって取引同一性ハッシュの一致だけを根拠に取引を単独で自動除外してはならず、取引を一意に突合する必要がある場合は元ファイル行番号を含む内部取引ID（11章）を用いる。このハッシュの用途は次の2つに限る。

- 使用用途修正版候補の照合（12.3）：2ファイル間で、取引同一性ハッシュを出現順に並べた列が一致（＝利用日・日本円請求額・正規化前の元利用店名・出現順が同一）し、かつ明細内容ハッシュが異なる場合に修正版候補として担当者へ提示する。出現順の一致判定はこの並びの比較で行い、ハッシュ自体には出現順を含めない。明細内容ハッシュはカード形式バージョンや元シート名の差でも変化するため、明細内容ハッシュの相違を使用用途だけの相違と等値にはせず、使用用途の相違か否かは12.3で担当者が確認する。
- 過去取引との部分一致警告（12.4）：出現順に依存させず、一致する取引同一性ハッシュの件数を警告として提示する。

## 12.2 同一内容の再アップロード

同一顧客内で明細内容ハッシュが一致する場合、別ファイルIDでも重複ファイルとして取込を停止する。別顧客間では重複判定しない。

## 12.3 使用用途だけ異なる再提出

利用日、金額、利用店名、明細順が同一で、使用用途だけが異なる別ファイルは「処理済み明細の修正版候補」とする。新規取込せず、担当者が使用用途更新または別取引として処理するか選択する。freee取込済みの場合は自動更新しない。

## 12.4 部分一致

新しいファイルの一部明細だけが過去取引と一致しても、ファイルIDが異なれば新規取引として取り込む。同日・同額・同店舗の正当な複数取引を誤除外しないため、行単位の一致だけでは自動除外しない。

ただし、一致行が存在する場合は取込を停止せず「過去取引との一致が○件ある」と警告し、該当行を表示する。

## 12.5 処理済みファイルの変更

処理済みファイルが同じDriveファイルIDのまま変更された場合、自動更新しない。「処理済みファイル変更」として要確認にし、担当者が取消し・差分反映・維持を判断する。

# 13. 取引先データ管理

## 13.1 正本

マスタースプレッドシートの共通取引先一覧を全顧客共通の正本とする。各顧客別スプレッドシートの取引先一覧へ一方向同期する。

同期範囲は保護し、顧客別スプレッドシートで直接編集できないようにする。顧客固有の変換は顧客別辞書で管理する。

## 13.2 初期移行

既存約2,900件を原本保持のうえ全件移行する。

- 同一摘要・同一取引先の重複は統合する。
- 同一摘要が異なる取引先へ対応する場合は「辞書競合」とする。
- 辞書競合は自動確定に使用しない。
- 移行前データと変換結果を保存する。

## 13.3 新規取引先

既存に適切な取引先がない場合、確認担当者は新しい取引先名の作成を申請できる。類似する既存取引先を表示し、重複作成を警告する。システム管理者が申請内容を確認し、全顧客へ影響する共通取引先一覧への登録として承認フローへ送る。オーナー管理者の申請は即時承認できるが、その場合も申請と承認を監査ログへ記録する（20.1）。他スタッフの申請はオーナー管理者の承認を必要とする。

承認後、共通取引先一覧へ新名称を追加し、対象顧客の取引先一覧へ同期する。あわせて、次回以降の自動判定のため顧客別辞書へ登録する（14.5）。承認前の名称をF列へ確定値として書き込まず、要確認を維持する。

現在の運用では、F列と取引先一覧に新名称を追加すれば、freeeインポート時に新規取引先として登録される前提とする。

要確認を解決する順序は、共通取引先一覧への登録、対象顧客の取引先一覧への同期、対象取引のF列更新、要確認の解決済み化（`partnerResolutionStatus`を`RESOLVED_WITH_PARTNER`とする）とする。対象顧客への同期が失敗した場合はF列を確定せず、要確認を維持する。他顧客への同期失敗は13.4に従って独立管理する。

## 13.4 同期失敗

共通取引先一覧（共通マスター）への登録、対象顧客の取引先一覧への同期、対象取引のF列更新のすべてが成功した場合にのみ、要確認を解決済みとする。F列更新の成功は、11.4に準じて書込み後の読取確認で判定し、書込要求の成功応答だけで解決済みにしない。いずれかが失敗した場合はF列を確定せず要確認を維持する。他顧客への同期失敗は独立して同期ログへ記録し、失敗顧客だけ最大3回再試行する。

# 14. 店名正規化と取引先判定

## 14.1 保持する名称

システム内部では次を分離する。

1. 元利用店名
2. 正規化利用店名
3. マッチした摘要・ルール
4. freee取引先名

元利用店名はK列およびログへ保存し、正規化処理で上書きしない。

## 14.2 正規化

判定用の正規化利用店名は、次の手順で生成する。

- 文字全体にUnicode互換正規化（NFKC相当）を適用し、半角カナを全角カナへ、全角英数字を半角英数字へ統一する。
- 英字は互換正規化後にすべて大文字へそろえる。
- 空白（全角スペース、連続する空白、タブ等）はASCII半角スペース1個へ統一する。
- 各種ハイフン・ダッシュ・長音類はASCIIハイフン（`-`）へ統一する。
- 文字列前後の空白を除去する。
- 不要な制御文字を除去する。

上記は判定用の正規化利用店名にのみ適用する。元利用店名はK列およびログに元のまま保持し、正規化結果で上書きしない。

## 14.3 正式な判定順序

```text
1. 顧客別辞書の元表記完全一致
2. 顧客別辞書の正規化完全一致
3. 共通取引先一覧・共通辞書の元表記完全一致
4. 共通取引先一覧・共通辞書の正規化完全一致
5. 承認済みパターンルール
   5-1. 顧客別
   5-2. 共通
6. 未承認の部分一致・類似一致
   → 候補提示のみ、必ず要確認
7. AI候補生成（後続フェーズ）
   → 候補提示のみ、必ず要確認
```

各段階で候補が一意の場合だけ自動確定する。複数候補、正規化衝突、辞書競合がある場合は信頼度差にかかわらず要確認とする。

## 14.4 承認済みパターン

完全一致、正規化一致、前方一致、部分一致等の一致方法、顧客ID、優先度、有効期間、登録者、承認者、登録日時、バージョンを保持する。

未登録の部分一致・類似一致は自動確定しない。人間が確認し、承認済みルールとなった後だけ次回から自動確定できる。

## 14.5 辞書学習

人間が確定した結果は、初期値として「顧客別・正規化完全一致」で登録する。必要なものだけシステム管理者が共通辞書へ昇格する。

共通辞書への昇格、共通取引先名変更、新形式有効化、全顧客同期は承認対象とする。オーナー管理者は自分の申請を即時承認できる。他スタッフの申請はオーナー管理者の承認を必要とする。

## 14.6 AI

Ver.1.0の完成条件にはAI候補生成を含めない。後続フェーズで追加する場合もAI結果は候補提示専用とし、信頼度にかかわらず人間確認を必須とする。顧客名、カード番号、名義、Drive URL、個人識別情報は送信しない。

# 15. 要確認処理

## 15.1 要確認シート項目

| 項目 | 内容 |
|---|---|
| ステータス | 未確認／確認中／解決済／対象外等 |
| 要確認種別 | 取引先、日付、金額、0円、形式、重複・変更、転記不整合等 |
| 取引ID | 不変の内部取引ID |
| 顧客ID・顧客名 | 対象顧客 |
| ファイルID・元ファイル名 | 原本識別 |
| 元シート・元行番号 | 元位置 |

| 元利用店名・正規化店名 | 判定材料 |
| システム候補 | 候補と判定方法 |
| 採用取引先 | 人間の確定値 |
| 日付・金額・使用用途 | 元値・修正値 |

| 登録日時・確認者・確認日時 | 監査情報 |

## 15.2 解決操作

担当者は要確認種別に応じて次を選択できる。

- 既存取引先を採用
- 新規取引先の作成を申請
- 取引先なしで確定
- 日付・金額等を修正
- 0円取引として計上
- 対象外
- 重複・変更候補を別取引として採用
- 元の処理結果を維持

取引先なしで確定した場合、F列は空欄のままだがステータスは解決済みとする。

F列の空欄だけでは、未確定と「取引先なしで確定」を区別できないため、取引ログには`partnerResolutionStatus`を保持する。少なくとも`UNRESOLVED`、`RESOLVED_WITH_PARTNER`、`RESOLVED_WITHOUT_PARTNER`を持ち、取込可否・要確認残数・完了判定はF列の表示値ではなくこの状態を使用する。

確認担当者は既存取引先の採用、取引先なし確定、日付・金額等の修正を行える。新規取引先作成は13.3の申請・承認手順を経る。システム管理者またはオーナー管理者であっても、権限に応じた承認記録を省略しない。

## 15.3 日付・金額修正

日付・金額の読取エラーは要確認シートで修正し、同じ取引IDの入力用シート行を更新する。元ファイルは変更しない。元値、修正値、確認者、確認日時を監査ログへ記録する。

# 16. freee取込管理

## 16.1 要確認残数の表示

要確認件数はマスターと顧客別転記先スプレッドシートの両方に表示する。取引列の構成は変更せず、専用表示領域またはメニューの警告ダイアログを使用する。

## 16.2 取込可否

- `partnerResolutionStatus=UNRESOLVED`だけであれば警告を表示し、担当者判断でfreee取込を許可する。F列空欄でも`RESOLVED_WITHOUT_PARTNER`は未確定件数へ含めない。
- 日付または金額の不正・空欄が残る場合はfreee取込を停止する。
- 未解決の0円明細等、計上可否が決まらない必須確認も停止条件とする。

## 16.3 freee取込済み

実際のfreeeインポート完了後、確認担当者がシステムメニューから対象取引を「freee取込済み」にする。登録前に17.4の整合性チェックを再実行し、対象件数、金額合計、未解決取引先件数、停止条件の有無を確認画面へ表示する。担当者が実インポート完了を明示的に確認した場合だけ登録する。データ作成・出力だけでは取込済みとみなさない。

freee取込管理には、取込バッチID、対象取引ID一覧または不変な処理単位、取込時点の各取引のB・F・I・K・M列ハッシュ、日時、実行者、未解決取引先ID一覧を保存する。一部だけをインポートした場合は、実際に取り込んだ取引だけを選択して別バッチとして登録する。

取込済み後にB・F・I・K・M列が変更された場合、取込時点ハッシュとの不一致を検出して「freee側も修正が必要」と警告する。取込時に未解決だった取引先を後から確定した場合も同じ警告対象とする。Ver.1.0ではfreee側を自動修正しない。

# 17. 手動変更・削除・取消し・復元

## 17.1 転記行の削除

処理済み取引IDが入力用シートに見つからない場合、「転記済み行が見つからない」として要確認にする。担当者は次を指示できる。

- 復元：取引ログの保存値からシステムが行を自動復元する。復元先は10.4の空き行判定で求めた未使用行とし、書込み後に取引ログの転記先行番号を実際に書いた行へ更新する。復元の書込みも11.4の読取確認と比較更新に従い、読取確認を終えてから転記先行番号を更新する。復元前に同一取引IDが既にいずれかの行へ存在する場合は書き込まず整合性エラーとして停止する。元の行位置へ戻すために既存データを押しのけて行を挿入してはならない。
- 削除として確定：復元せず、取引状態を`DELETED_ACCEPTED`へ更新（比較更新）し、削除者、確認者、日時、理由を記録する。

## 17.2 手動変更

B・F・I・K・M列が手動変更されている場合、勝手に上書きしない。担当者が「手動変更を採用」または「システム保存値へ戻す」を選び、変更前後を監査ログへ保存する。

## 17.3 取消し

実行IDまたはファイル単位で、未freee取込の転記行、要確認、辞書候補を取り消せる。取消時に次を選択する。

- 未処理へ戻し、修正後に再処理する。
- 【取消済】として通常処理から除外する。

いずれの場合も対象取引の状態を`CANCELED`へ更新（比較更新）する。未freee取込の転記行はB・F・I・K・M列と内部取引ID列をクリアして10.4の空き行へ戻し、11.3の再開回復が取消し済み取引を`COMMITTED`へ再確定したり、残存行が空き行判定を妨げたりしないようにする。取引ログの取消し済み記録は転記先行情報を残したまま無効化して監査に用いる。

「未処理へ戻し、再処理する」を選んだ場合、同一取引IDの再登録が比較更新（11.2）で阻害されないよう、取消し済みの取引ログ記録を明示的に無効化（supersede）してから再取込する。無効化した記録は重複判定（12.2）の対象から除外し、無効化と再登録は監査ログへ記録する。これにより、内容が変わっていない取消し済みファイルを再処理しても、明細内容ハッシュ一致による重複停止で再取込が妨げられないようにする。

freee取込済み取引は自動削除せず、管理者確認とfreee側の修正を要求する。取消理由、実行者、日時を監査ログへ記録する。

freee取込済み取引の取消しを確定できるのはシステム管理者またはオーナー管理者とする。確認担当者は取消申請まで行える。

## 17.4 整合性チェック

新規取込開始前および「freee取込済み」にする直前に、取引ID重複、行欠落、手動変更を検査する。不整合があれば処理を止め、担当者の判断を求める。

# 19. 同時実行・継続・再試行

## 19.1 同時実行

同じ顧客・ファイルを他担当者が処理中の場合はスキップし、処理者と開始時刻を表示する。他顧客の処理は継続する。LockServiceと永続的な処理リースを併用する。

LockServiceのスクリプトロックは、処理リース取得・更新および転記先行の予約に必要な短時間だけ保持し、ファイル解析中や人手待ちの間は保持しない。処理リースには顧客ID、ファイルID、実行ID、処理者、取得日時、最終ハートビート、状態を保存する。

同じ顧客の異なるファイルを並行解析することは許可するが、同じ転記先スプレッドシートへの空き行判定・行予約・書込みは顧客単位または転記先単位で直列化する。これにより、別ファイルが同じ空き行を選ぶ競合を防ぐ。行予約時点で内部取引IDを書込み、予約後の処理は11章に従って冪等に完了させる。

継続トリガーへ処理を引き渡す場合は、同じ実行IDでリース所有者だけを更新する。リース期限切れを理由とする自動奪取は行わず、19.3に従って管理者が再開を指示する。継続トリガーの起動時は、自らが現在も有効なリースの所有者（同一実行ID）であることを確認してから継続する。所有権が別の実行IDへ移っている場合、またはリースが解放済み（内部状態が`VALIDATING`・`WRITING`以外へ遷移、7.2）の場合は継続せず、自身の一時トリガーを削除する。

## 19.2 実行時間上限

GASの実行時間上限が近づいたら安全な位置で処理状態を保存し、一時的な継続トリガーを作成して自動再開する。全件完了後に一時トリガーを削除する。これは定期自動取込ではなく、担当者が開始した1回の処理の継続である。

実行時間の上限秒数と安全余裕秒数は実行環境ごとに設定値として保持する（本文中に30分等の固定値を記載しない）。1回の処理の経過時間が「上限秒数 − 安全余裕秒数」に達する前に、書込みを安全な区切りで止めて状態を保存し、継続処理へ移る。環境や実行者権限で上限が変わる場合は、それぞれに対応する設定値を用いる。

## 19.3 異常終了

ハートビート更新が一定時間途絶えた取引を「中断」と判定するのは、内部状態が`VALIDATING`または`WRITING`の場合に限り、ファイル名の【処理中】接頭辞だけを根拠にしない。`REVIEW_WAIT`・`CUSTOMER_FIX_REQUIRED`・`FAILED`はハートビートが更新されなくても中断とみなさない（7.2）。中断と判定した場合は管理者へ通知する。予期しない異常終了は自動引継ぎせず、管理者の指示で取引IDを確認して続きから再開する。

## 19.4 再試行

Drive、Sheets等の一時的エラーは間隔を空けて最大3回自動再試行する。日付不正、転記先形式不一致、形式不明等、再試行で直らないエラーは即時要確認とする。

# 20. 権限・セキュリティ

## 20.1 役割

| 役割 | 主な権限 |
|---|---|
| 確認担当者 | 要確認の修正・確定、取引先なし確定、新規取引先の作成申請、freee取込済み登録 |
| システム管理者 | 新規取引先申請の確認、カード形式下書き、処理引継ぎ、同期再実行 |
| オーナー管理者 | 新規取引先承認、共通辞書承認、共通名変更、形式有効化、一括同期、復元 |

全顧客に影響する操作は申請・承認制とする。他スタッフの申請はオーナー管理者が承認する。オーナー管理者自身の申請は即時承認でき、他者承認を必要としない。

役割は包含関係とし、オーナー管理者はシステム管理者・確認担当者の権限を、システム管理者は確認担当者の権限を持つ。ただし申請者・承認者・実行者は監査ログで別項目として記録し、実行権限を持つことを理由に承認記録を省略しない。オーナー管理者の自己申請は申請と承認を同一人物・同一時刻で記録する。

処理対象顧客はユーザーごとの許可顧客IDで制限する。確認担当者をはじめ各ユーザーが、許可されていない顧客の明細、候補、ログを閲覧・更新できないよう、メニュー表示だけでなくサーバー側関数の入口でも顧客単位で認可する。役割の包含関係は操作権限の広さを表すものであり、許可顧客IDによる顧客単位の制限とは独立に検証する。

## 20.2 シート保護

共通取引先一覧、共通辞書、カード形式マスター、監査ログ、顧客別同期範囲、内部取引ID列を保護する。変更はシステム操作画面経由に限定する。

## 20.3 外部入力の安全化

利用店名、使用用途等の文字列は、Sheets APIの`RAW`相当または`Range.setValue()`で文字列型として書き込み、対象セルの表示形式をプレーンテキストにする。`=`、`+`、`-`、`@`等で始まる値をGoogle Sheetsの数式として実行させない。安全化のために論理値へ余分な文字を付加せず、K列とログから元の文字列を再現できるようにする。元ファイル内の数式自体を転記先へコピーしない。

## 20.4 個人情報

カード番号、カード名義は保存不要とする。実ファイルはアクセス制限し、自動テストには構造を維持した匿名化コピーを使用する。

## 20.5 実行者識別と自動継続

対話操作ではGoogle Workspaceの実行者メールアドレスを、顧客マスターまたは権限マスターの許可ユーザーと照合する。実行者を信頼できる方法で取得できない場合は権限操作を拒否し、匿名または空文字の実行者で処理しない。

一時トリガーによる自動継続は、トリガーを実行するアカウントと処理開始者を分けて記録する。継続処理は開始時に許可済みだった処理範囲だけを引き継ぎ、新しい承認、辞書登録、取込済み登録等の人間判断を代行しない。

# 22. 既存ロジックとの並行比較

導入初期は既存F列数式の判定結果と新システムの判定結果を内部的に比較する。不一致は自動確定せず要確認にする。

既存F列数式相当の判定結果は、転記前プレビュー段階で、検証用の複製シートまたは計算用領域において評価・保存する。その評価・保存を終えた後に、本番の入力用シートへ新システムの値を書き込む。並行比較のために本番のF列へ旧数式を一時的に挿入してはならない。

並行比較終了条件は次のすべてとする。

- 1か月以上運用
- 1,000明細以上を処理
- 重大な自動誤判定0件
- オーナー管理者の終了承認

# 23. テスト・導入

## 23.1 環境分離

テスト用マスター、Driveフォルダ、転記先コピーを本番環境から分離する。テスト環境から本番URL・ファイルIDへ書き込めないようにする。

## 23.2 回帰テスト

既知4カード形式は、匿名化した実構造サンプルの全明細について、日付、金額、利用店名、使用用途、除外判定を期待値と照合する。1項目でも不一致なら不合格とする。

最低限、次を試験する。

- 通常明細、ETC、返品、負数、0円
- ご入金・合計・キャッシング・見出し除外
- 半角カナ、全角英数字、文字コード差
- 年なし日付、Excelシリアル値、海外利用
- 使用用途不足とファイル名補完
- 複数シート、形式不明、0件明細
- 同一内容再アップロード、使用用途修正版、部分一致警告
- 書込後ログ前の異常終了、名称変更失敗
- 2人同時実行、自動継続、最大3回再試行
- 要確認確定の二重実行
- 手動削除・変更、復元、取消し
- 転記先列変更、数式行不足
- 数式インジェクション文字列
- freee取込済み後の変更警告

## 23.3 性能試験

20顧客、100ファイル、5,000明細を1回の全件処理として開始し、一時トリガーによる継続を含めて最後まで完了できることを確認する。

## 23.4 段階導入

最初は2～3顧客で試験運用し、並行比較条件を満たした後に対象顧客を順次増やす。対象外顧客は現行手作業を継続する。
