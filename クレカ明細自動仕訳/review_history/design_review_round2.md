# Critical（8件）

## CR1. ログアーカイブがファイル状態の正本を消し、処理済みファイルが再検出されて二重転記する
3.33.4のアーカイブ対象に「クレカ処理ログ」が含まれ、④で元シートから削除する。3.8モード1のフィルタは「内部状態: DISCOVEREDまたは未登録」で、`createProcessLog`はファイルごとに1行しか作らない。
保存年数を過ぎた`COMPLETED`ファイルの処理ログ行を削除すると、そのファイルは「未登録」になる。Driveに`【済】...csv`が残っていれば次回の未処理検索で候補に上がり、**全明細が新しい実行IDで再転記される**。取引ログも同時に消えるため仕様11.3の冪等判定も効かない。
仕様7.1「ファイル名は表示であり処理状態の正本は内部ログ」をアーカイブ自身が破っている。
→ 消えない恒久インデックス（ファイルID・内部状態・元ファイル名・各ハッシュ・hashVersion のみの軽量シート）を新設し、モード1のフィルタと仕様12.2の重複判定はこれを参照する。

## CR2. 取引ログのアーカイブで重複判定の材料が消え、同一明細が再取込される
退避条件が「終端状態かつ有効=FALSE **または対応ファイルがCOMPLETED/CANCELED/EXCLUDED**」のため、正常完了した取引がそのまま削除対象になる。
`checkPurposeRevisionCandidate`（仕様12.3）も部分一致警告（仕様12.4）も取引ログから取引同一性ハッシュを取る。アーカイブ後は「過去取引が存在しない」状態になり、顧客が同じ期間の明細を使用用途だけ直して再提出すると**修正版候補として検出されず全件取り込まれる＝二重転記**。アーカイブ先を検索する経路はどこにも定義されていない。
→ 重複判定に必要な最小列（取引ID完全値・取引同一性ハッシュ・明細内容ハッシュ・hashVersion・ファイルID・freee取込状態）を退避対象から除外して恒久保持する。

## CR3. 年補完アルゴリズムが実データの常態で1年ずれた日付を自動確定する（複数の独立した欠陥）
3.14 `inferYearsForFile` に、レビューで4つの異なる誤りが見つかった。いずれも`ambiguous: false`で自動確定するため要確認にもならない。

1. **年境界を含まないファイル**：`decreaseCount === 0` で全件に基準年を適用する。「2026年1月請求」の締め期間は通常2025/11/16〜2025/12/15で、**明細に1月の行が1件も現れないのが常態**。月列`[11,11,12,12]`は減少0回なので、全件が2026-11-15/2026-12-03という未来日付になる。
2. **降順ソートのファイル**：出現順が昇順である前提が明記も検証もされていない。降順で年境界をまたぐと月列は`[1,1,12,12]`となり、減少1回なので1月に2025年・12月に2026年が割り当たる（真値と逆）。
3. **12→1以外の逆転**：減少判定が大小比較のみで年境界かを検証していない。3/15の次に2/20が来るだけで前半全体に`baseYear - 1`が付く。
4. **基準年の意味づけ**：`(i < decreaseIndex) ? baseYear - 1 : baseYear` は「基準年＝年境界の後半」を前提とするが、`extractYearFromFilename`等が請求年を返すのか利用年を返すのかが未定義。

→ 出現順の増減ではなく**請求年月（基準年月）との相対関係**で決める。`baseYear`/`baseMonth`を確定し、`月 > baseMonth + 許容ラグ`の行を`baseYear - 1`とする。基準月を取得できない場合は`ambiguous: true`。割当て後に単調性を検証し、単調でなければ要確認。補完後の日付が現在日付を超える場合は無条件に`ambiguous`とするサニティチェックを入れる。`extract*`関数は年ではなく`{year, month}`を返し、「請求年月を返す」と意味づけを明記する。

## CR4. `registerReview` の重複抑止キーが粗く、取引単位の要確認が1件しか登録されない
3.25の`registerReview`は「同一ファイル・同一種別で`OPEN`の行があれば重複登録しない」とし、取引ID完全値を含まない。
1ファイル内に取引先未解決が30件あっても`PARTNER`要確認は1行しか登録されない。残り29取引は`REVIEW_REQUIRED`・F列空欄・`UNRESOLVED`のまま要確認一覧に現れない。「全件解決後→COMPLETED」が要確認件数基準なら1件解決でファイルが完了し、3.27の停止条件も同様に潰れるため、**未解決取引先や不正日付を抱えたままfreee取込済みに進める**。
→ 抑止キーを種別で分ける。取引単位種別（`PARTNER`/`DATE`/`AMOUNT`/`ZERO_AMOUNT`/`INTEGRITY`）は「取引ID完全値＋種別」、ファイル単位種別のみ「ファイルID＋種別」。「全件解決」の判定を要確認件数ではなく`partnerResolutionStatus`と`transactionStatus`で行うと明記する。

## CR5. 取消し→再処理で同一取引IDが2行になり、比較更新と全検索関数が破綻する
取引IDは`(顧客ID, ファイルID, シート名, 行番号)`の決定的ハッシュなので、取消し後に同じファイルを再処理すると必ず同一IDになる。設計はsupersede（有効=FALSE）するが、`findTransactionRow`/`getTransactionLog`/`getTransactionsByStatus`のいずれにも「有効=FALSEを除外する」規定がない。
再登録時の`updateTransactionStatus(txId, null, 'PREPARED')`がsupersede済みの`CANCELED`行を拾い、`ALLOWED_TX_TRANSITIONS[CANCELED] = []`なので回避もできず、**仕様17.3が明示的に用意した「未処理へ戻して再処理」の経路が常に失敗する**。
→ 取引ログの一意キーを「取引ID完全値＋有効=TRUE」と定義し、全単一取得関数に有効=TRUEフィルタを明記。有効=TRUE行が2行以上なら`IntegrityError`で停止。

## CR6. 空き行判定がLockServiceの排他区間の外にあり、同一行を二重予約できる
3.23の書込フローは「1.空き行判定 → 1'.テンプレート行拡張 → 2.行予約（LockService排他）」で、排他がステップ2にのみ掛かる。
仕様19.1は「同じ転記先スプレッドシートへの**空き行判定**・行予約・書込みは顧客単位または転記先単位で直列化する」と、空き行判定を明示的に直列化対象に入れている。判定がロック外だと、同一顧客の2ファイルを並行処理した際に両者が同じ空き行集合を得て、後勝ちで先のファイルの取引ID列が上書きされ、**先の取引は行を失ったまま`COMMITTED`になり得る**。
→ 「空き行判定 → テンプレート行拡張 → 行予約」を1つのロック区間に入れる。ロック内で予約対象行が空であることを読み直して確認する。

## CR7. 「処理中ファイルを再開」が起動する遷移が遷移表に存在しない
3.2と4.2は「ハートビート途絶ファイルを`→ VALIDATING`で再開」と書くが、`ALLOWED_TRANSITIONS`に`VALIDATING → VALIDATING`も`WRITING → VALIDATING`もない。`transitionFileState`が先頭で検証するため**必ず`StateTransitionError`で失敗する**。Ver.1.1のM1〜M8と同型の配線漏れが1箇所再発。
→ 4.2を「途絶検知時にまず`→ FAILED`へ遷移させ、`FAILED → VALIDATING`で再開する」2段階へ改め、3.2の「起動する遷移」欄も`→ FAILED → VALIDATING`とする（4.4の取消し2段階化と同じ形）。

## CR8. `detectProcessedFileChange` が未変更ファイルを全件「変更あり」と誤判定する
`scanProcessedFilesForChange`はメタ情報が未変化ならハッシュを`null`のまま返すのに、受け側は`processLog.fileBinaryHash !== currentHash`で比較する。未変更ファイルでは保存済みハッシュ（文字列）≠`null`となり、**登録済み全ファイルに毎回`FILE_CHANGED`要確認が起票される**。CR4で作った独立フローが機能しない。
→ `const hashChanged = (currentHash !== null) && (processLog.fileBinaryHash !== currentHash);` とする。

# Major（主要なもの）

## アーキテクチャ・GAS実現性（仕様側の見直しが必要なもの）

### MA1. シート保護では「システム操作画面経由のみ」を実現できない（仕様20.2が実装不能）
コンテナバインドのGASスクリプトは**実行者の権限**で動作するため、Sheetsの保護は「人が手で編集する」ことと「同じ人がメニューからスクリプトを動かして編集する」ことを区別できない。保護から実行者を除外すればスクリプト自身が書けなくなり（取引ID列への書込・監査ログ追記が失敗）、実行者を許可すれば手編集も防げない。Sheetsの保護に「追記専用」モードは存在しない。
3.22検証項目7が「取引ID列の保護範囲が正しく設定されていること」を必須検証にしているため、**正しく設定するほど書込が失敗する構造**になっている。
→ 設計判断を選ぶ必要がある：(a) 保護は警告用途（`setWarningOnly(true)`）とし、書込はオーナー権限で動作するウェブアプリまたはApps Script API経由に限定する、(b) 監査ログは「追記専用保護」ではなく「オーナーのみ編集可＋前行チェーンハッシュによる改竄検知」で担保する。**仕様20.2の書き換えを伴う。**

### MA2. バージョン付きデプロイはバウンドスクリプトのメニュー実行に効かない（仕様18.5が実装不能）
8.3は「本番のデプロイを新バージョンへ切り替え」「直前安定版デプロイIDへ切り戻す」とするが、バウンドスクリプトのメニュー関数・トリガーは**常にHEAD（保存中のコード）を実行**し、バージョン付きデプロイは参照されない。「デプロイIDを切り戻す」操作は本番挙動を1バイトも変えない。
→ (a) 実処理をライブラリ（バージョン指定参照）へ切り出す、(b) `clasp`でGit管理しロールバックを「安定版タグの`clasp push`」と定義する、のいずれか。**仕様18.5の解釈を確定する必要がある。**

### MA3. LockServiceの使い方がAPI仕様と合わず「顧客単位の直列化」は実現できない
`getScriptLock()`はロックオブジェクトを返すだけで取得しない（`tryLock`/`waitLock`が必要）。解放も`lock.releaseLock()`。またScriptLockはスクリプト全体で1本しかなく、**顧客単位の粒度は存在しない**。「同じ顧客の異なるファイルは並行解析できる」という設計の性能前提が誤り。
→ `tryLock`の戻り値を必ず判定し、失敗時は`LEASE_CONFLICT`相当でスキップすると明記。5.2の「顧客単位」を「スクリプト全体で直列化される」へ訂正。`LOCK_TIMEOUT_MS`を`SETTINGS`へ追加。

### MA4. リースの強制解放手段がなく、`ACTIVE`残留で恒久デッドロックになる
仕様19.1どおり自動奪取はしないが、**管理者がリースを解放する操作・関数・メニュー項目が定義されていない**。GAS実行が強制終了するとリース行は`ACTIVE`のまま残り、以後そのファイルは`acquireLease`が必ず`LEASE_CONFLICT`を返して永久に処理できない。8.3のロールバック手順も「ACTIVE が0件」を前提にしているためコードのロールバックもできなくなる。
→ `forceReleaseLease(leaseId, reason, actor)`をシステム管理者操作として追加。前提条件（`VALIDATING`/`WRITING`かつハートビート途絶超過）と監査ログ記録を規定。

### MA5. 処理リースシートが無制限に増加し、`acquireLease`が毎回全走査する
`releaseLease`は行を消さず`RELEASED`にするだけで、3.33.4のアーカイブ対象にも含まれない。リース行は処理のたびに1行増え永久に残る。LockService排他下で毎回全走査するため**ロック保持時間が単調増加**し、仕様19.1「ロックは短時間のみ保持」を破る。
→ `releaseLease`で監査ログへ1行書いてリース行自体を削除する。

### MA6. 4.5の再走査が全`COMPLETED`ファイルに対して毎回Drive APIを呼ぶ
`scanProcessedFilesForChange`は対象状態の全処理ログ行に`getFileMetadata`を1件ずつ呼ぶ。絞込も上限もない。運用2年後に顧客1,000ファイル×20顧客なら1回で**20,000回のDrive API呼出**となり`MAX_DRIVE_CALLS_PER_RUN`を確実に超える。「通常処理の開始前に自動実行」なら通常の取込が毎回クォータで止まる。
→ 対象を直近N日＋freee未取込を含むファイルに限定。`Files.list`の1回のページングでまとめて取り、メモリ上で突合する。「開始前に自動実行」は削除し明示メニュー実行のみとする。

### MA7. `detectPostImportChange`・整合性チェックが取引1件ごとにシートを読む
仕様23.2「明細1行ごとのAPI呼出しを基本実装にしない」に真正面から反する。取込済み5,000取引で5,000回の読取となり実行時間上限とクォータの両方を超える。3.24検査2・検査3、`recoverPartialFailure`内の`findRowByTransactionId`も同様。
→ 転記先の対象範囲を`values.batchGet`で1回だけ読み、取引ID→行のインデックスをメモリ上に構築してから照合する。3.24・3.27も同じインデックスを共有する。

## ロジック・整合性

### MA8. `probeLogAppend()`が必須ログを汚染し、並行実行時に実ログ行を削除する
処理ログに`appendRow`でダミー行を追記し`deleteRow(getLastRow())`する。追記と削除の間に別実行が本物のログ行を追記すると**実ログ行を削除する**（排他なし）。処理ログは冪等性判定の正本であり、1行消えるだけでCR1と同じ二重転記経路に落ちる。例外時はダミー行が恒久的に残る。
→ プローブ先を専用の使い捨てシート（1セル）へ変更し、`setValue`の成否だけを見る（行の増減を伴わない）。

### MA9. 3.17の照合条件が移行データ・学習結果と矛盾し、取引先判定が常に0件になる
3.17は「各段階の照合対象は有効=TRUEかつ承認済みの行に限る」と全段階へ一律適用するが、8.1の移行登録も3.18の学習登録も承認済みをTRUEにする記述がない。結果、移行した2,900件も人間が確定した学習結果も`承認済み=FALSE`のままでStep1〜Step4が1件もヒットしない。
仕様14.3はStep1〜4（完全一致）とStep5（承認済みパターン）を明確に分けており、承認要件を課すのはStep5以降。
→ Step1〜4は`有効=TRUE`のみを条件とし、`承認済み=TRUE`を要求するのはStep5（`prefix`/`partial`）に限る。2.1.5 J列の説明も「一致方法が`prefix`/`partial`の行にのみ意味を持つ」と定義し直す。

### MA10. `recoverPartialFailure`が参照する`hasReviewItems`の格納先が取引ログにない
再開時の最終状態を`txLog.hasReviewItems`1つで決めているが、取引ログに該当列がなく導出規則も未定義。`undefined`は偽なので**要確認を残す取引まですべて`COMMITTED`へ確定される**。Ver.1.1のM1〜M8と同型。
→ 2.1.9へ「要確認保持フラグ（予定最終状態）」列を追加し、書込前登録時に確定して保存する。

### MA11. F列確定後に読取確認値を更新しないため、解決済み取引が全件「手動変更」と誤検知される
`FIX_DATE_AMOUNT`には「予定値・読取確認値を更新」と明記があるが、`ADOPT_EXISTING_PARTNER`等にはない。3.24検査3は「`COMMITTED`の行が読取確認値と異なるか」で判定するため、要確認で確定したF列はW列が空欄のままとなり、**次回の整合性チェックで解決済み取引がすべて`INTEGRITY`要確認になる**。整合性チェックは新規取込開始前に走るため実運用で毎回止まる。
→ シート値を変更した操作は必ず予定値（Q〜U列）と読取確認値（V〜Z列）を同時更新する、という不変条件を3.23冒頭へ置く。

### MA12. `NEEDS_FREEE_FIX`からの復帰経路がなく、整合性チェックが恒久的に例外で停止する
3.24検査4は対象を`IMPORTED`に限定する条件がなく、`NEEDS_FREEE_FIX`からの遷移先も定義されていない。一度この状態になった取引は次回も同じ不一致を検出し、比較更新が現在値不一致で失敗して`StateTransitionError`を送出する。**該当取引が1件でもある顧客は以後すべての処理が開始できない**。
→ 検査4の対象を`IMPORTED`に限定。`ALLOWED_FREEE_TRANSITIONS`を3.1に定義し、解決操作`CONFIRM_FREEE_FIXED`を3.25へ追加。

### MA13. 明細内容ハッシュを上書き再計算するため「同一ファイルの再提出停止」が効かなくなる
4.3は「明細内容ハッシュを再計算し処理ログM列を更新」とするが、M列は仕様12.2の重複判定に使う「提出時点の明細内容」のハッシュ。日付・金額を修正するとM列が修正後の内容に置き換わり、顧客が**同一の元ファイル**を再提出しても一致せず全件が再取込される＝二重転記。
→ M列は提出時点のハッシュとして不変とし、修正後のハッシュが必要なら別列を追加する。

### MA14. `ALLOWED_TX_TRANSITIONS`に`PREPARED/WRITING → CANCELED`がない
ファイル側にはM20で`VALIDATING → CANCELED`・`WRITING → CANCELED`が追加されたが、取引側の`CANCELED`遷移元は`COMMITTED`と`REVIEW_REQUIRED`だけ。`VALIDATING`中／`WRITING`中のファイルを取消すと**ファイル側だけ`CANCELED`になり取引ログが`PREPARED`のまま取り残される**。
→ `PREPARED → CANCELED`、`WRITING → CANCELED`を追加。

### MA15. 読取確認の比較正規化が未定義で、B列が恒常的な`DESTINATION_VALUE_MISMATCH`を招く
B列を`USER_ENTERED`で`'yyyy-MM-dd'`として送るとシート側では日付シリアル値になるが、取引ログの予定値・読取確認値は「文字列」と定義。`valueRenderOption`も未定義で、`FORMATTED_VALUE`ならロケール依存、`UNFORMATTED_VALUE`ならシリアル値。いずれも一致せず**全取引が停止する**。
→ 読取は`UNFORMATTED_VALUE`＋`FORMATTED_STRING`固定と明記。列ごとの正規化比較規則を表で定義し、`verifyWrittenValues`・`valuesMatchExpected`・3.24検査3・`hashRowValues`が共有する。

### MA16. `values.batchUpdate`の「1リクエストにまとめる」が誤りで、障害注入点が実際の分割点を覆っていない
`valueInputOption`はリクエスト単位のフィールドでレンジごとに変えられない。実装は正しく2回呼んでいるが本文4箇所が「1リクエスト」と書いている。結果、**RAW成功／USER_ENTERED失敗という部分書込状態が実在する**のにその扱いが書かれておらず、障害注入点も`SHEET_WRITE_BEFORE`/`AFTER`がループの外にあるため2リクエストの間で停止させる試験ができない。
→ 記述を「`valueInputOption`ごとに最大2リクエスト」へ統一。部分書込は仕様11.3 Step4で回復する旨を明記。障害注入点を4点へ細分。送信順はRAW（取引ID列を含む群）を先に固定。

### MA17. `hashRowValues()`が定義されていない
仕様16.3の中核（取込時点ハッシュとの比較）に使うが、算出規則（列の順序、null/空欄の扱い、Date・数値の正準化、`hashVersion`との関係）が一切ない。同種の問題で指摘された`dataHash`は3.33.3で規則化されたのに取り残されている。
→ `cellToCanonicalString`＋`serializeDeterministic`で規定し、3.33.3と共有関数にする。

### MA18. 文字化け判定3により、未登録のカード形式が必ず「文字化け」として顧客へ差し戻される
判定3「ヘッダー期待キーワードがどの候補エンコーディングでも一致しない→文字化けの疑い」は、**未登録の新形式では正しくデコードできていても当然一致しない**。結果`ENCODING_DETECTION_FAILED`（対応者＝顧客）となり、`UNKNOWN_CARD_FORMAT`（対応者＝システム管理者、「新しい明細形式を登録する」）に到達しない。仕様7.3・8.3の新形式登録導線が機能しない。
→ 判定3を単独の失格条件から外し、判定1・2が閾値を超えた場合のタイブレークにのみ使う。

### MA19. `stripPrefixes`が顧客由来の`【…】`を破壊し、年補完・使用用途補完の根拠を失う
`/^(?:【[^】]+】)+/`は先頭の任意の`【…】`をすべて除去し、結果を「元ファイル名」として以後不変で保存する。顧客が`【2026年1月】ご利用明細.csv`や`【仕入】明細.csv`で提出するのは普通にあり、初回検出時に潰されると年補完の根拠と使用用途補完キーワードが失われる。Drive上の顧客の元ファイル名も恒久的に失われる。
→ 除去対象を`STATE_TO_PREFIX`の値集合から生成した正規表現に限定する。

### MA20. `classifyValidationResult`が`duplicateResult`を判定に使っておらず、重複ファイルが区分3で転記される
入力仕様に列挙されているが本体のどの分岐でも参照されていない。区分判定関数が「事前検証結果の正本」である以上、実装は重複ファイルをそのまま`WRITING`へ進めて**全件を二重転記**する。
→ 区分2群の先頭に重複停止の分岐を追加し、`ERROR_CATALOG`へ`DUPLICATE_CONTENT`を追加。

### MA21. `ADOPT_AS_NEW_TRANSACTION`/`APPLY_FILE_DIFF`が取引ID生成規則と矛盾する
取引IDは決定的ハッシュなので「新しい取引ID」を生成する手段が設計内に存在しない。また変更ファイルの先頭付近に1行挿入されると**以降の全行の行番号がずれ、全取引が差分と判定されて全件追記される**。
→ `ADOPT_AS_NEW_TRANSACTION`を削除するか取引ID要素に再取込世代番号を追加。`APPLY_FILE_DIFF`の差分は行番号ではなく取引同一性ハッシュの多重集合差分で求め、一定割合を超える場合は取消し→再取込へ誘導。

### MA22. freee取込対象の抽出に`transactionStatus`の条件がなく、未転記取引を「取込済み」にできる
`PREPARED`/`WRITING`のまま残っている取引が取込バッチに含まれ`IMPORTED`になる。その後11.3の回復処理が走ると、既に取込済みとされた取引の行を新規に書き込むことになりfreee側との整合が最初から崩れる。
→ 対象を`COMMITTED`/`REVIEW_REQUIRED`かつ有効=TRUEかつ転記先行番号設定済みに限定し、`PREPARED`/`WRITING`が残る場合は停止条件に加える。

### MA23. `=== true`の厳密比較がシート由来の真偽値で破綻し得る
競合フラグ・有効フラグに`=== true`を使っているが、シートからの読取値は`valueRenderOption`や表示形式によって文字列`'TRUE'`になり得る。`conflictFlag === true`が偽に落ちると**辞書競合が自動確定され**（仕様13.2違反）、`isActive === true`が偽に落ちると**重複判定が常に「重複なし」**になる（二重転記）。どちらもエラーにならず静かに壊れる。
→ `toBool(v)`を90_Utilsに定義し、シート由来の真偽値はすべて通す。読取時に行オブジェクトへ正規化して詰める方式を規定する。

### MA24. XLSX変換後のシートで元ファイルの物理行番号が保たれる保証がない
読取方法が未定義。`getDataRange().getValues()`を使うと先頭に空行があるファイルでデータ開始位置がずれ、配列インデックス＋1が物理行番号と一致しない。仕様11.1は「行番号がぶれると同一取引が再実行時に別IDとなり二重転記の原因になる」と明示的に警告している。
→ `getRange(1, 1, getMaxRows(), getMaxColumns()).getValues()`で1行目から読むと固定し、「同一ファイルを2回変換して`sourceRow`が一致すること」を受入条件にする。

### MA25. `incrementQuota`をAPI呼出「後」に計上し、書込直後に例外を投げるため取引境界での停止にならない
値書込が成功した直後・読取確認と取引状態更新の前に例外が飛ぶ。取引は`WRITING`のまま、シートには値が入った状態で実行が終わる。仕様23.2「取引境界で状態を保存」「部分書込を起こさない」に反する。
→ `incrementQuota`は計上と接近フラグ設定のみ行い例外を投げない。呼出元が各バッチ完了後に`isQuotaExceeded()`を確認して安全に離脱する。

### MA26. `APPROVE_COUNT_MISMATCH`の「`REVIEW_WAIT`のまま転記処理へ進む」が状態遷移表にない
`ALLOWED_TRANSITIONS[REVIEW_WAIT]`に`WRITING`が含まれない。加えて件数・合計不一致は区分2＝無書込で`REVIEW_WAIT`に落ちているため、この時点でパース結果も取引IDもメモリ上に存在せず「そのまま転記へ進む」ことは物理的に不可能。
→ 「`REVIEW_WAIT → VALIDATING`へ遷移して事前検証ブロックへ再合流（再検証時は照合不一致を区分2にしない）」へ書き換える。`RESIZE_INPUT`も同様。

### MA27. 3.25の解決操作の実行権限が3.4・3.28・仕様20.1と矛盾する
3.25の解決操作はすべて「要確認を確定」メニュー（確認担当者）から選択できるが、`RESTORE_ROW`はオーナー管理者、`REGISTER_FORMAT`はシステム管理者、`RESIZE_INPUT`はオーナー管理者承認対象。特に復元は取引ログの保存値からシートへ書き戻す破壊的操作。
→ 解決操作表に「必要役割」列を追加し、`resolveReview()`の入口で操作コードごとに`authorize()`を呼ぶと規定する。

### MA28. 並行比較の複製シートについて行の選び方・例外時の後始末・セル数上限への影響が未定義
複製先がどのスプレッドシートかも定義されていない。顧客の転記先スプレッドシート内なら、中断のたびに巨大な複製シートが残り**顧客の出納帳のセル数上限（1,000万）を消費**する。
→ 複製先を作業用の一時スプレッドシート（処理後にゴミ箱へ）と規定し、`try/finally`で確実に削除する。

### MA29. `updateFilePrefix`の`DriveApp.getFileById`がtry外にあり、ファイル削除で顧客ループ全体が停止する
顧客が`【要修正】...csv`をゴミ箱へ入れると例外が伝播し、`retryPendingRenames`が顧客ループ先頭で呼ばれるため**その顧客の処理が毎回冒頭で全滅する**。
→ try内へ移し、ファイル不在と権限不足を区別。ファイル不在は再試行しても直らないため`FAILED_MAX_RETRY`として管理者通知。ループは1件の例外で中断しない。

### MA30. `faultInjectionPoint`が環境判定を持たず、本番発火・性能劣化の двух риска
本番保護が3.6の起動時検証だけに依存しているが、05_SettingsValidatorを呼ぶのは4.1と4.2のみで、**4.3・4.4・3.27は検証を経ずに停止点へ到達する**。加えて呼出のたびにScript Propertiesを読むため5,000明細で10,000回以上の読取が発生する。
→ 先頭に本番マスターID判定の自己防衛ガードを入れ、設定は実行開始時に1度だけ読んでキャッシュする。

### MA31. 2.1.2.1の初期投入データ「ファイル種別 `csv/xlsx`」が2.1.2の許容値に反する
2.1.2のE列は「`csv` / `xlsx`」の単一値・必須なのに、投入表は4形式すべて`csv/xlsx`。等値比較する実装だと**初期4形式すべてが一度も一致せず**`UNKNOWN_CARD_FORMAT`になる。
→ E列を複数値許容（JSON配列）と定義し直す。
