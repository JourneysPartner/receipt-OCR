# Critical（約12件）

## 分類1：データ破壊・二重転記（沈黙して壊れる）

### CR-A. 空き行判定が既存の手入力行を上書きする ★顧客データ破壊
- **出典**：B-C6 / 5.11 空き行判定表 L2241-2246
- 使用中の判定が「取引ID列に値／B・I・K・M列のいずれかに値／**既存手入力行として識別できる**」だが、3つ目の**判定基準が本書にも仕様書にも一切定義されていない**（仕様10.4の文言をそのまま写している）。
- 転記先は顧客が現に使っている freee クレカ出納帳。勘定科目だけ先に入れた行、freee側の都合でB列を空にした行は**B・I・K・Mがすべて空**になり得る。この行は空き行と判定され**システムが上書きする**。仕様3原則6・25.1最終項に正面から違反。上書きされた側は取引ログに存在しないため整合性チェックでも検出されない。
- → 空き行の定義を「**ヘッダー定義範囲内の全列が空**」へ変更。`DestinationIndex`の取得範囲をB列〜最終データ列へ広げる（1回のバッチ取得で済むためINV-08と両立）。INV-27を追加。

### CR-B. 年補完が処理日に依存し、同一ファイルの再提出で重複停止が効かない
- **出典**：B-C5 / 5.1 規則6第1項 L1991、5.6 L2142、6.1 L2288-2290
- 規則6が「補完後日付が**処理日**より未来ならファイル全体を曖昧」とし、明細内容ハッシュは補完**後**の日付から計算される（6.1の順序が 8-6年補完 → 8-8重複チェック）。
- 1月20日提出：01/25が未来→曖昧→全行`date=null`→ハッシュH1。2月5日に同内容を再提出：01/25は過去→日付が入る→ハッシュH2≠H1。**重複判定が成立せず二重転記**。
- → 明細内容ハッシュを**年補完前の値**（年なしなら`--MM-DD`）から計算する。`hashVersion`を上げる。規則6の未来判定を「処理日」でなく「**基準年月の翌月末**」との比較に変えれば処理日依存を根絶できる（推奨）。INV-26を追加。

### CR-C. 規則5に `baseYear + 1` の枝がなく、11か月ずれた年を確定し得る
- **出典**：B-C4 / 5.1 規則5 L1985-1988、ケース11 L2012
- 規則5は`baseYear−1`と`baseYear`しか返さず、**基準年月より後の利用日を表現できない**。ケース11（基準2025-12、行01/10）は`1 ≦ 12`→**2025-01-10**。真値は2026-01-10で11か月ずれる。
- 設計は「規則6の遡り超過で救済」としているが、その救済は`YEAR_INFERENCE_MAX_LOOKBACK_MONTHS`という**単なるチューニング設定**に依存する。運用者が誤検知を減らそうとこの値を上げた瞬間、**1年ずれた日付が静かに自動確定される**。3ラウンド潰し損ねた欠陥と同種のものが設定値の裏に残っている。
- → 候補年`{baseYear−1, baseYear, baseYear+1}`のうち許容窓`[base − LOOKBACK, base + FORWARD]`に入るものを選ぶ。**該当が0個または2個以上なら要確認**。`YEAR_INFERENCE_MAX_FORWARD_MONTHS`（既定1）を新設。受入条件へ「**設定値をどう変えても誤った年が自動確定されないこと**」を追加。

### CR-D. 使用用途修正版候補が「警告」止まりで、仕様12.3の「新規取込せず」を満たさない
- **出典**：A-29 / 5.10 区分判定表 L2228、4.14 L1164-1173、6.1 L2290
- 5.10の区分2の該当条件に**修正版候補が入っていない**。修正版候補は定義上、明細内容ハッシュが**異なる**ため`DUPLICATE_CONTENT`にも該当しない。6.1のstep 8-8は「修正版候補・部分一致は**警告**」と明記。
- 設計どおり実装すると**警告を出したうえで全件転記される**。顧客が使用用途だけ直して再提出する運用は前提とされており（仕様12.3・24.2）、そのたびに二重転記。CR2が防いだ事象が別経路で残っている。
- → 5.10の区分2へ「使用用途修正版候補」を追加。4.14の異常系表へ対応行を追加。6.1 step 8-8を「修正版候補も区分2の材料。部分一致のみ警告」へ。5.8ケース3の期待出力へ「取込停止（区分2）」を明記。

### CR-E. CSV解析規則が消滅し、取引IDが非決定になる
- **出典**：A-1 ＋ B-M10 / 4.10 L1027-1041、INV-12 L562、4.20 L1313
- 仕様6.1「引用符内のカンマ・改行等はCSV規則に従って解析する」が設計から完全に消滅（「引用符」「RFC」「BOM除去」の記述がゼロ）。Ver.1.2では`parseCsv`の擬似コード内にしか無かった。
- 引用符内改行を含む1レコードは**物理行を2行以上占める**。実装者Aが「レコード番号」、Bが「先頭物理行番号」を採れば取引IDが変わる。**取引IDが変われば仕様11.3 Step5へ落ちて全件が新規行として追記＝全件二重転記**。利用店名の複数行商品名で実際に発生する。
- → 4.10の契約へ「RFC 4180に従う。`rows[i]`は**論理レコード**であり、各レコードは`startPhysicalRow`（先頭物理行番号、1起算）を保持する。**取引ID生成に用いる元ファイル行番号は`startPhysicalRow`とする。レコード番号を用いてはならない**」。INV-12へ同旨を明記。受入条件「引用符内改行を含むサンプルを2回読み込み、全レコードの`startPhysicalRow`が一致すること」。

### CR-F. BOM未除去で初期4形式のうち2つが判定不能
- **出典**：B-M9（Critical相当） / 5.2 判定表 L2023-2027
- 仕様6.1は「UTF-8（BOM有無）を自動判定する」を要求するが、5.2にBOMの検出も除去も規定がない。
- BOMを除去せずデコードすると先頭セルが`﻿利用日`になる。`rakuten`と`amazon_mc`は**1行目のキーワードで判定する**ため一致せず`UNKNOWN_CARD_FORMAT`。**Excelで保存されたCSVはBOM付きが常態**であり、初期4形式のうち2つが最も一般的な保存形式で判定不能。仕様25.1「既知4形式を一意に判定できる」が達成不能。
- → 5.2冒頭へ判定0を追加：「先頭が`EF BB BF`ならUTF-8と確定し**BOMを除去してからデコードする**。`FF FE`／`FE FF`は`ENCODING_DETECTION_FAILED`。判定0成立時は判定1〜3を行わない」。

## 分類2：可用性・デッドロック（動かなくなる）

### CR-G. 「オーナー管理者のみ編集可」が確認担当者の通常処理を全面的に不能にする ★最優先
- **出典**：B-C1 / 9.1 保護方針表 L2477-2483、INV-22 L572
- 9.1が「共通取引先一覧、共通取引先辞書、**顧客別取引先辞書**、カード形式マスター」「監査ログ」を**オーナー管理者のみ編集可**としている。だがINV-22自身が「保護から実行者を除外するとシステム自身が書き込めなくなり、取引ID列への書込と監査ログ追記が失敗する」と警告している。
- 実行形態はコンテナバインドで、コードは**メニューを押したスタッフの権限**で動く。したがって：
  - 確認担当者の処理 → 6.1 step 9-9 辞書学習が**顧客別取引先辞書**へ書込 → 保護違反
  - `releaseLease`が**ファイル1件ごとに**監査ログ追記（INV-20）→ 保護違反 → `REQUIRED_LOG_WRITE_FAILED` → 以降の転記書込を開始しない
  - 6.3の新規取引先承認後フローStep1も同様
- **結果、オーナー管理者以外は1ファイルも処理できない。**
- **注記**：これは仕様Ver.2.1で20.2を改訂した際、当方が「重要マスターはオーナー限定」と書いたことに起因する。仕様側の記述が不正確だった。
- → 9.1から**顧客別取引先辞書と監査ログをオーナー限定編集から外す**（全員編集可＋警告付き保護＋連鎖ハッシュ／整合性チェックで検知）。オーナー限定にできるのは「オーナーしか実行しない操作でしか書き込まれないシート」に限る。9.1の各行へ「書き込むモジュールとその実行者の役割」を列として追加。**仕様20.2も併せて訂正が必要。**

### CR-H. 監査ログの連鎖ハッシュが並行追記とアーカイブで恒久破損し、全停止する
- **出典**：B-C2 ＋ B-M22 / INV-21 L571、4.33 L1764、4.34 L1797、4.24 検査7 L1496
- `appendAudit`の契約に**ロックの要求が一切ない**。また監査ログは4.34の退避対象でINV-05の恒久保持対象にも入っていない。
- 3つの独立した破綻：
  1. **並行追記**：2人が同時に追記すると同じ直前ハッシュを持つ2行が生まれ、`verifyChain`が必ず不一致→`AUDIT_CHAIN_BROKEN`。監査ログは追記専用で修正不可なので**恒久的に壊れたまま**。
  2. **その帰結が全停止**：検査7は**新規取込開始前に毎回**走る。一度の並行追記で**全顧客の取込が永久に開始できなくなる**。
  3. **アーカイブが先頭行を消す**：`LOG_RETENTION_YEARS`を設定した瞬間に`verifyChain`が必ず不一致になりシステム停止。
- さらに検査7は監査ログ**全走査**（年5万行のSHA-256再計算を取込のたび）でINV-25と仕様23.2に反する。
- → (1)`appendAudit`を`tryLock`取得済みの排他区間内に限定。(2)**アンカー行**を導入し`verifyChain`はアンカー以降のみ検証（ログアーカイブ台帳G列をアンカーの正本に）。(3)検査7を毎回検査から外し日次トリガーまたは直近N行のみへ。(4)破損時の帰着を「全停止」から「**管理者へ通知し、破損位置を記録して以降は新チェーンとして継続**」へ。INV-29を追加。

### CR-I. INV-17の完了判定が、取消し済み取引を含むファイルを永久に完了させない
- **出典**：B-C7 / INV-17 L567、4.26 `EXCLUDE` L1559
- INV-17は「全取引が`COMMITTED`／`CANCELED`／`DELETED_ACCEPTED`のいずれか、**かつ**`partnerResolutionStatus`が`UNRESOLVED`でない」を完了条件とする。一方`EXCLUDE`はpartnerResolutionStatus欄が「変更なし」。
- 取引先不明の1件を「対象外」で解決すると`CANCELED`かつ`UNRESOLVED`になり、**永久に第2条件を満たさない**。他の全明細を解決してもファイルは`REVIEW_WAIT`から抜けられず、担当者に回復手段がない。`ACCEPT_DELETION`も同型。
- → INV-17を「……かつ**`transactionStatus`が`COMMITTED`である取引に限り**`partnerResolutionStatus`が`UNRESOLVED`でないこと」へ。`EXCLUDE`／`ACCEPT_DELETION`の欄へ「変更なし（**完了判定の対象外**）」を明記。

### CR-J. `APPROVE_COUNT_MISMATCH` が承認を永続化せずライブロックする
- **出典**：B-C9 / 5.9 ケース7 L2220、4.26 L1570
- 「再検証時は照合不一致を区分2にしない」とあるが、**「承認済み」という事実を記録する列がどこにもない**。再検証で`verifyCountsAndTotals`は当然また不一致を返す→区分2→新しい要確認が登録され→`REVIEW_WAIT`へ戻る。**無限ループ**。
- → 処理ログへ「照合不一致承認」「承認者・承認日時」列を追加し、`verifyCountsAndTotals`の契約へ「承認済みなら`ok = true`を返す」を追加。INV-28を追加。

### CR-K. 恒久取引インデックスが無限成長し、INV-05とINV-25が両立しない
- **出典**：B-C8 / 2.1.16 L519、INV-05 L555、INV-25 L575、4.21 L1342
- 2.1.16は「**いかなる契機でもアーカイブ・削除しない**」と定め、明細1件＝1行で永久に増える。一方INV-25は「全登録ファイル・全取引を無条件に走査する経路を作らない」。だが4.21の重複判定・部分一致・修正版候補照合は恒久取引インデックス参照以外の方法が示されておらず、**分割・圧縮・維持の仕組みが一切ない**。
- 受入規模を月次とすると年6万行、5年で330万セル。取引ログ・処理ログ・監査ログと`SPREADSHEET_CELL_LIMIT`を共有するため運用数年でセル上限に到達。到達時は`LOG_CAPACITY_EXCEEDED`＝システム停止だが、**INV-05により削除できない**（INV-05と4.37の相互デッドロック）。
- → (1)恒久取引インデックスを**専用スプレッドシートへ分離**し、**顧客ID単位でシートを分ける**（走査範囲が顧客単位に閉じ、仕様12.2「別顧客間では重複判定しない」とも整合）。(2)年度単位の分割・ロールオーバー規則を定義し維持責務を61_TransactionLogへ。(3)**ファイル単位の重複判定は2.1.15のみで完結**させ、取引単位インデックスを引くのは修正版候補照合と部分一致警告に限り**直近Nか月へ絞る**。(4)4.37へ専用スプレッドシートのセル数を独立指標として追加。

## 分類3：過少定義（実装できない）

### CR-L. 「請求年月」の意味も抽出規則も未定義で、初期4形式では抽出不能
- **出典**：B-C3 / 5.1 規則2・3 L1980-1981、2.1.2 Q列 L165、2.1.2.1 L174-194
- 年補完の全体が`(baseYear, baseMonth)`に依存するが、(a)「請求年月」が**支払月・締め月・利用月のどれか**未定義、(b) Q列のJSONスキーマが存在しない、(c) **初期4形式にQ列の値が1つも与えられていない**、(d) 期間を単一の`(year, month)`へ還元する規則がない。
- 初期4形式すべてで基準年月を取得できず**全ファイルが曖昧**→年なし日付が全件要確認。dカード・セゾンは年なし日付が常態であり**実質的に全明細が手作業に戻る**。
- さらに規則3「1つでも異なる値を示した場合は確定しない」が致命的。日本のカード明細は**ファイル名＝支払月、ヘッダー＝利用期間**の組合せが常態で、両者は必ず異なる`(year, month)`を返す。ケース7はこれを「曖昧」と正解扱いしているが、**これは例外ではなく常態**。設計どおり実装するとほぼ全ファイルが曖昧になる。
- → (1)「請求年月」を「**当該ファイルの明細が属する利用期間の終了年月（締め年月）**」に固定。支払月しか得られない形式はマスターに`締めから支払までのオフセット月数`を持たせ締め年月へ正規化。(2)Q列のJSONスキーマを定義。(3)**2.1.2.1へ4形式それぞれのQ列初期値を追加**。(4)規則3を「**正規化後の締め年月が一致するときのみ確定**」へ。

### CR-M. 決定的直列化の長さ単位と正規化が未定義で、全ハッシュが実装者依存
- **出典**：B-C10 / 5.6 L2120-2132、4.38 L1923、4.20 L1306
- 「各要素の長さ情報を区切りとして連結する」だけで、(a)長さが**UTF-8バイト数／UTF-16コード単位／コードポイント数**のどれか未定義、(b)「正規化後の文字列で算出」の正規化が何を指すか不明（NFKCなら元利用店名を正規化してはならない規定と矛盾）、(c)区切り記号が未定義。L2132は問題を認識しながら**どちらを採るか決めていない**。
- この関数は**取引ID完全値・明細内容ハッシュ・取引同一性ハッシュ・dataHash・hashRowValues・監査ログ連鎖ハッシュのすべての土台**。実装者がUTF-16長で書き後にUTF-8長へ「修正」した瞬間、**全既存取引IDが再現しなくなり全件二重転記**。半角カナ・絵文字は実データで普通に出現する。
- → 逐語定義を置く：「`s = 正準化文字列(e)`（**文字列にはいかなる追加の正規化も適用しない**）、`utf8Len(s)`を**UTF-8バイト数**とし、連結は`utf8Len(s) + ":" + s`を要素順に結合。`null`／`undefined`は`"-1:"`。ハッシュ入力は結合結果のUTF-8バイト列」。受入条件として**16進固定値**の期待値を6ケース（サロゲートペア・半角カナ・空文字列・null・区切り文字を含む文字列）持つ。

### CR-N. スナップショット復元が三重に欠落し、受入必須項目が検証不能
- **出典**：A-7 / 2.1（シートなし）、4.34 L1775-1808
- (a) **2.1にスナップショットの保存先シートがない**（ログアーカイブ台帳は新設されたのに）。`snapshotId`が何を指すのか、世代管理をどう実現するのか未定義。(b) **復元を実行する関数が存在しない**（`verifyRestore`は照合するだけ）。4.4の「復元」も4.30の承認対象の「復元」も文脈上は転記行の復元を指す。(c) 仕様23.6が要求する**件数・バイト数の記録**が`takeSnapshot`の保証項目にない。
- 仕様25.1の受入必須項目1件と24.3の試験1件が**設計から検証不能**。
- → (1)「復元用スナップショット台帳」シートを追加。(2)`restoreFromSnapshot(snapshotId, targetSpreadsheetId, approver)`を追加し、契約に「オーナー管理者の承認を必須」「復元後に必ず`verifyRestore`を実行し不一致なら確定しない」を置く。(3)`takeSnapshot`の保証へ件数・バイト数を追加。4.4の「復元」を2行に分ける。

# Major（主要なもの）

## 振る舞い表・年補完の周辺
- **M1**：5.1ケース6の中間値が規則5と食い違う（`3 ≦ 3`なので2026-03-25が正しいのに2025-03-25と記載）。結論は偶然一致するが、この表は実装者がテストの期待値にそのまま使う
- **M2**：規則6第2項（遡り超過の単独行）でB列へ値を書くのか空欄にするのか未規定。素直に実装するとケース11で**2025-01-10（真値より11か月前）が出納帳に書かれる**
- **M3**：遡り上限の比較粒度（年月単位／日単位）が未定義。既定3か月は支払月基準だと正常明細を全件フラグする。カード形式マスターへ「遡り許容月数」列を追加すべき
- **M4**：補完後日付の実在性検証がない。基準2025-03・行`02/29`→`new Date(2025,1,29)`は例外を投げず**2025-03-01**を返す。真値は2024-02-29。1日ずれが要確認にもならず自動確定
- **M5**：未来日1行でファイル全体を曖昧にすると、500行中1行の後日確定で**500件の要確認が登録される**。「基準年月そのものが未来」と「個々の行が未来」を分けるべき
- **M6**：`extractBillingYearMonth`が`null`一本で「取得元なし」と「取得元が矛盾」を区別できない。候補年が呼出側へ届かず規則8を満たせない。対応者も異なる（前者=顧客、後者=システム管理者）

## GAS実現性
- **M7**：5.5の`dateTimeRenderOption = FORMATTED_STRING`が、同節が禁じたロケール依存を持ち込む。表示形式が`M月d日`の顧客では年が復元できず**全取引が`DESTINATION_VALUE_MISMATCH`**。`SERIAL_NUMBER`へ変更すべき
- **M16**：`ScriptApp.getProjectTriggers()`は**実行者自身のトリガーのみ**返す。`reclaimOrphanTriggers`の保証が成立せず、他ユーザーの残留を回収も検出もできない。`MAX_TRIGGERS`が「ユーザーあたり」である点も未記載
- **M24**：SpreadsheetApp（テンプレート複製・書式）とSheets API（値書込・読取）の混在で`flush`順序が未規定。読取確認が旧値を返すと**全取引が`DESTINATION_VALUE_MISMATCH`**
- **M29**：`getRange(1, 1, MAX_ROWS_PER_FILE, ...)`はグリッドを超えると例外。`MAX_ROWS_PER_FILE = 10,000`を素直に指定すると**ほぼ全ファイルで例外**
- **M30**：`PASTE_FORMULA`は「値のセルは値を」貼り付ける。テンプレート行のB・M列に値が残っていると複製先にコピーされ、直後の空き行判定が使用中と判定→**拡張が永久に空き行を作れない無限ループ**
- **M23**：分あたりレート制限（429）の規定がない。バックオフの算式が未定義で、5,000明細を`WRITE_BATCH_SIZE=200`で処理すると同じ分の中で3回とも失敗して確定エラー

## 抽出・判定
- **M8**：5.2ケース4とケース6が同一入力に対して異なる出力を定義。実装次第で**新形式登録導線が永久に機能しない**欠陥（MA18で潰したもの）が戻る
- **M11**：連続空行20行での打切りが警告なしに明細を取りこぼす。照合材料のない形式では**何も検出されない**過少計上
- **M12**：`saison`／`rakuten`／`amazon_mc`の除外ルールに合計行・ご入金行がなく、**合計行が取引として行を確保し取引IDまで書かれる**
- **M13**：カード形式マスターN・O・P・Q列（JSON）のスキーマがどこにも定義されていない。**カード形式判定・明細抽出・件数合計照合・年補完の4つの中核機能が実装不能**
- **M25**：辞書の有効期間（H・I列）が5.7の照合条件に現れず、**期限切れルールが自動確定に使われる**。優先度F列も死んだデータで、実装者が使うと要確認へ回すべきケースを自動確定する
- **M26**：取引同一性ハッシュが「提出時点」か「現在値」か未規定（INV-07は明細内容ハッシュしかカバーしない）

## 状態・フロー
- **M15**：処理ログの行の粒度（実行×ファイル／ファイル）が未定義で`updateProcessLog(fileId, …)`と矛盾。INV-05が検証不能
- **M17**：6.1 step 9-3のファイル変更ガードが予約**後**にあり、中止すると取引ID列だけ入った行が残る。5.11は使用中と判定するため**バッチサイズ200なら1回で200行が死ぬ**。次回再開時は回復Step4が**変更されたファイルの内容を無検証で書き込む**
- **M18**：`TRANSACTION_ID_COLLISION`の帰着状態・リース解放・要確認種別が未定義。リースが解放されず**そのファイルは以後永久に処理できない**（`forceReleaseLease`まで30分待ち）
- **M19**：`MULTI_SHEET`に「対象シートを選ぶ」解決操作がなく、**複数シートXLSXは何度再検査しても同じ結果で永久に処理できない**
- **M20**：区分2で停止したファイルは取引ログに1行も登録されないため、`isFileFullyResolved`が**空集合に対して真**になり、**1行も転記していないファイルが【済】になる**
- **M28**：「処理中ファイルを再開」の遷移が4.2（`→ FAILED → VALIDATING`）と6.2（`FAILED → VALIDATING`）で食い違い、**同一操作に2つの正解**がある
- **M31**：年あり日付にサニティチェックが一切かからない。`2035/01/05`が無検査で出納帳へ。2桁年の世紀規則も未定義

## 仕様カバレッジ・内部整合（A側）
- **A-6**：取消しが**要確認と辞書候補に触れていない**（仕様17.3は3つが対象）。孤児の要確認が残り、再処理時に抑止キーが効いて新しい要確認が登録されない
- **A-12**：整合性検査が「**3者照合**」になっていない（仕様23.4）。検査7項目すべてが2者どまりで、ファイル状態との突合がゼロ
- **A-21**：**依存関係が循環している**（`04_Notifications ↔ 66_QuotaManager`）。12章は自ら「循環参照は許可しない」と書いた章
- **A-19**：カード形式マスターI列が必須のため、**日付代替列（M列）が定義上どの形式でも使えない**
- **A-20**：恒久取引インデックスH列（freee取込状態）の更新責務が未定義で、**再走査の絞込が機能せずDrive API全走査に戻る**
- **A-23**：取引先要確認の登録時点が8-10と9-8で二重規定。8-10で登録すると区分1・区分2に落ちたファイルで**孤児の要確認だけが残る**
- **A-25**：自動確定時に`partnerResolutionStatus`を`RESOLVED_WITH_PARTNER`とする規定がなく、**自動確定率100%のファイルでも`COMPLETED`にならない**
- **A-18**：INV-10の相互参照が2つとも誤った節を指す（4.11→4.9、4.31→4.32）
- **A-30**：ファイル内部状態の正本が仕様29.1（処理ログ）と設計（恒久ファイルインデックス）で**真逆**。どちらかを宣言する必要がある
- **M14**：4.22の必須検証項目2・5・6が「期待どおり」としか書かれておらず実装不能。不合格は`DESTINATION_SCHEMA_MISMATCH`＝書込全面停止という重い帰着を持つ
- **M21**：並行比較の複製先を別スプレッドシートにすると、旧F列数式が参照する取引先一覧が`#REF!`になり**評価不能**。全取引が要確認へ落ちる
- **M27**：5.10の区分判定表に文字コード判定失敗が現れず、INV-14の「表が正本」と矛盾

3. **5.7の取引先判定の照合順序** ── 承認済み条件をStep5に限定した修正は正しく、「判定が常に0件」という致命的欠陥を確実に解消
4. **5.8の変更検出表とINV-24** ── 「未取得のnull」と「不一致」の区別は正しい
5. **7.1のLockService分析** ── GASの実仕様どおり。性能前提を撤回した判断も「誠実」
6. **6.4の取消し2段階フロー** ── 遷移表と完全に整合し、仕様17.3の要求も満たす
7. **10.3のロールバック手段** ── バウンドスクリプトの前提が正しく、clasp＋安定版タグへの切替は妥当
8. **INV-02/04/08/09/11/13/16/19/20/23/24** ── 検査可能な形になっており受入試験にそのまま使える。特にINV-09とINV-04は過去の失敗を的確に不変条件へ昇華している
