## C2. 処理リーステーブルが存在しない

## C4. 処理済みファイル変更検出が構造的に到達不能
- 3.8 DriveScannerのフィルタは「内部状態: DISCOVEREDまたは未登録」で `COMPLETED`/`REVIEW_WAIT` は候補に出ない。

- 仕様12.5・仕様25.1（受入必須）が永久に満たされない。
- 修正：DriveScannerに「処理済みファイル再走査モード」を追加。`COMPLETED`/`REVIEW_WAIT`/`FAILED`の登録済みファイルについて`modifiedTime`・リビジョン・バイナリハッシュのみ比較し、変化があれば内部状態を遷移させずに`FILE_CHANGED`要確認だけを起こす独立フローとして4章に節を切る。

## C5. REVIEW_WAIT を再開・再検査する導線がメニューに存在しない

## 分類2：新規コードの誤り

### M9. recoverPartialFailure Step5 が取引状態を更新しない
Step3・Step4は`COMMITTED`/`REVIEW_REQUIRED`へ更新するのに、Step5は`writeToRow`→`verifyWrittenValues`→`continue`で終わる。書込完了なのに`PREPARED`/`WRITING`のまま残り、`WRITING`滞留が仕様19.3の中断誤検知とアラートを誘発。仕様11.3第5項＋第3項。
→ Step5の`verifyWrittenValues`直後にStep3/4と同じ状態更新を追加。

### M10. hasEverBeenCommitted が死条件
Step1が抽出するのは`PREPARED`と`WRITING`のみ。仕様11.2が「`COMMITTED`から`PREPARED`等への直接復帰は行わない」と定める以上、`hasEverBeenCommitted`は常にfalse。仕様11.3第6項の「既に`COMMITTED`なのに現在値が異なる」ケースが到達不能。
→ 3.23へ「`COMMITTED`取引の現在値ずれは3.24 44_IntegrityCheckerの『手動変更』検査で検出し仕様17.2の手動変更フローへ回す」と明記。4.2で`44_IntegrityChecker`を`recoverPartialFailure`の前に実行する順序がこの役割分担を担保する旨を注記。死条件分岐は削除するか比較更新の競合検知として残す旨を明示。

### M11. detectProcessedFileChange の対象状態が狭い
対象が`COMPLETED`/`REVIEW_WAIT`のみ。仕様11.5が守るのは「すでに取引行を確保したファイル」であり、`WRITING`中に中断して`FAILED`になったファイルも行を確保済み。`FAILED`ファイルが差し替えられた後に再開指示すると別の取引IDが生成され、既存の予約行が孤児化したまま二重転記になる。
→ 条件を `COMPLETED`/`REVIEW_WAIT`/`WRITING`/`FAILED` に拡張。`CUSTOMER_FIX_REQUIRED`は仕様11.5前段により意図的に除外する旨をコメントで明記（無書込のため再検査時に取引IDを生成し直すのが正しい）。

### M12. checkLogCapacity の判定式が容量を測っていない
`getLastRow()/getMaxRows()` は「割り当て済み行のうち使用済み行の割合」でしかない。ログシートは`appendRow`で行が自動拡張されるため常に100%近辺に張り付き、95%で`LogCapacityError`を投げる実装では通常運用中に転記が停止する（恒久的な偽陽性）。実際の制約であるスプレッドシート1ファイル1,000万セル上限とDriveストレージ残量を見ていない。仕様23.6。
→ 指標を「スプレッドシート全体のセル数（全シートの`getMaxRows() × getMaxColumns()`合計）／10,000,000」へ変更。`DriveApp.getStorageUsed()`/`getStorageLimit()`も判定に加える。「実際に1行追記して例外が出るか」のフェイルセーフを併用。閾値はM8のとおり設定値化。

### M13. inferYear が年境界を扱えない
ファイル名／請求年月から単一の年を決めて全件に適用する実装。請求年月2026年01月の明細には12/28（2025年）と01/05（2026年）が同居するのが常態で、12/28を2026-12-28として11か月未来の日付を確定する。`uniqueYears.length === 1`は年境界の曖昧さを検出できず`ambiguous: false`で自動確定してしまう。仕様9.3・25.1（受入必須）。
→ ファイル単位のアルゴリズムへ変更：(1)明細を元ファイルの出現順に並べ月の系列が単調非減少かを確認、(2)月が減少する箇所（12→1）が1回だけならその前後で年を1年ずらす（基準年＝請求年月の年を後半に割り当て、前半に年−1）、(3)月の減少が2回以上／出現順が信頼できない場合は`ambiguous: true`で全件要確認。

### M14. inferYear が仕様外の根拠（アップロード日時）から年を返す
`uniqueYears.length === 0`の分岐が`{ year: yearFromUploadDate, source: 'UPLOAD_DATE' }`を返す。仕様9.3が認める補完根拠はファイル名／請求年月／ヘッダーの3つのみ。`ambiguous: true`でも`year`を使えば根拠のない年が転記される。`context.uploadDate`未定義時に例外にもなる。`source`の三項式も複数根拠一致時の記録が不正確。
→ 当該分岐は`{ year: null, source: null, ambiguous: true }`を返して要確認とし、アップロード年は要確認画面の参考候補としてのみ表示。`source`はヘッダー由来を含む3値とし、複数根拠一致時は両方を記録。

### M15. serializeDeterministic の null/undefined 処理がない
`Utilities.newBlob(e)`に`null`/`undefined`が渡ると例外。`generateContentHash`は`tx.merchantOriginal`と`tx.purpose`を、`generateIdentityHash`は`merchantOriginal`をそのまま渡す。仕様9.5は空の元利用店名を明示的に許容し、仕様9.6も空欄使用用途の存在を許す。空欄取引を含むファイルでハッシュ生成が落ちる。`null`と`''`を区別しないと衝突も生じる。
→ `serializeDeterministic`へ正規化を組み込む（`(e === null || e === undefined) ? ' NULL' : String(e)`）。バイト長は正規化後の文字列で算出。「バイト長プレフィックス＋文字列連結」は長さがバイト単位・連結が文字単位で自己記述的復号ができない旨を注記し、`hashVersion`変更時に全バイト列ベースへ移行できるようにする。

### M16. verifyRestore の dataHash が未定義かつ join が非決定的
(1)`snapshot.dataHash`を比較するが、スナップショット内容の定義（3.33）に`dataHash`がなく生成規則も未定義。(2)`restoredData.map(row => row.join('\t'))`はセル値が`Date`の場合ロケール依存文字列を生み（仕様23.8に反し環境で値が変わる）、セル内容にタブが含まれると区切りが曖昧になる。仕様23.6・23.8。
→ スナップショット内容へ`dataHash（SHA-256）`を追加し「行ごとに`serializeDeterministic(row.map(cellToCanonicalString))`を適用し結果全体をさらに`serializeDeterministic`してSHA-256」と規則を定義。`cellToCanonicalString`はDateを`Utilities.formatDate(v,'Asia/Tokyo','yyyy-MM-dd')`、数値を整数/10進表記、その他を文字列として正規化。取得側と検証側で同じ関数を共有する旨を明記。

## 分類3：フロー・順序の誤り

### M17. 転記先形式検証が WRITING 遷移後に置かれている
4.1は「`WRITING`へ遷移 → 42_SheetSchemaValidator」の順。仕様9.8区分2は転記先形式不一致を「ファイル全体を無書込で管理者確認（`REVIEW_WAIT`）」と定め、仕様10.6も「書込前に検証」と規定。3.14の`classifyValidationResult`にも転記先検証が組み込まれていない。
→ 4.1で`42_SheetSchemaValidator`を`30_TransactionValidator`と同じ事前検証ブロック（`VALIDATING`中）へ移し、区分2判定の入力に含める。`WRITING`遷移は区分3確定後のみとする。

### M18. テンプレート行の拡張が値書込の後に置かれている
3.23は「1.空き行判定 → 2.行予約 → 4.値書込 → 5.読取確認 → 6.テンプレート行拡張」の順。テンプレート行を使い切った時点では手順1で空き行が見つからず手順6に到達しない。仕様10.5。
→ 「1.空き行判定 → 空き行不足なら 1'.テンプレート行拡張（コピー元行の構成検証合格が前提、不正なら停止）→ 2.行予約 …」へ組み替える。

### M19. 35_ParallelComparator の呼び出し位置が3箇所で食い違う

## 分類6：Ver.1.1修正の未達

### M35. ハイフン正規表現がリテラル文字のまま
3.16は`s.replace(/[‐‑‒–—―−ー－ｰ]/g, '-')`でコードポイントescapeになっておらず、直後の表もヘッダーが「コードポイント」なのに中身は文字そのもの。`‐`(U+2010)・`‑`(U+2011)・`­`(U+00AD)・`-`(U+002D)はソース上で視認区別できず、この修正が排除しようとした曖昧さが残っている。
→ `s = s.replace(/[‐‑‒–—―−ー－ｰ]/g, '-');` とし、表のコードポイント列を`U+2010`形式に置き換える。

### M36. STATE_TO_PREFIX が未定義／updateFilePrefix が元ファイル名を劣化させる
(1)3.9の`STATE_TO_PREFIX[toState]`が設計書のどこにも定義されていない（00_Configには`FILE_PREFIX`しかなく、内部状態→接頭辞の写像が存在しない。`DISCOVERED`は空文字列を返す必要がある）。(2)`baseName`を「現在のファイル名から接頭辞を剥がした結果」として算出しており、初回検出時の元ファイル名を正本にしていない。顧客が手動改名した場合や過去の改名失敗で接頭辞が二重に付いた場合、元ファイル名が恒久的に劣化する。(3)`/^【[^】]+】/`は1個しか除去しないため二重接頭辞状態から遷移すると蓄積する。仕様7.4。
→ 00_Configへ`STATE_TO_PREFIX`（`DISCOVERED: ''`を含む全9状態）を定義。`baseName`はクレカ処理ログの「元ファイル名」列から取得。接頭辞除去は`/^(?:【[^】]+】)+/`とする。

## 分類7：過剰

### M37. テンプレート行の存在を全顧客の必須スキーマ要件にしている
