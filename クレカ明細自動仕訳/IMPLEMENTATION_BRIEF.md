# 1. この設計書の読み方

普通の詳細設計書と構造が違う。**擬似コードが1行もない。** これは意図的なもので、経緯がある。

初期版には擬似コードがあったが、5ラウンドのレビューでも欠陥が減らなかった。年補完アルゴリズムは3ラウンドで5つの異なるバグが見つかり、それでも直りきらなかった。**実行もテストもできないコードをレビューで正しくする、という方法が機能しなかった。**

そこで擬似コードを全部削り、次の3つに置き換えた。

| 種類 | 場所 | 実装での使い方 |
|---|---|---|
| **契約** | 第4章 | 関数の署名・保証・事前条件・事後条件・異常系。**実装の輪郭** |
| **不変条件** | 第3章 | 破ると何が壊れるかまで書いてある。**受入検査の項目** |
| **振る舞い表** | 第5章 | 入力→期待出力の表。**そのままテストコードにする** |

**アルゴリズムをどう書くかは実装者が決めてよい。** 振る舞い表の全ケースが通り、不変条件を破らなければ、実装の形は問わない。

# 2. 実装順

## 原則
第12章のトポロジカル順序に従う。ただし**フェーズは依存順ではなく「テストの安さ」で切る**。

固定値の期待値を持つものから作る。理由は上記のとおり、この案件では「動かして確かめられないもの」が繰り返し壊れたため。

## フェーズ0：期待値が固定されている純粋関数
外部サービスに一切触れない。ここは**書いた瞬間にテストできる**。

| 対象 | 期待値の所在 |
|---|---|
| `serializeDeterministic` / `sha256` | **5.6.5 に16進の固定値ベクトル7件。** サロゲートペア・半角カナ・空文字列・`null`・区切り文字を含む文字列を含む |
| `00_Config` の定数・列挙 | 第4章4.1、第11章（設定63キー） |
| `06_ErrorCatalog` | 第4章4.7 |
| 正規化（`normalize`） | 5.x の正規化手順表 |

**`serializeDeterministic` を最優先で固める。** 取引ID・明細内容ハッシュ・取引同一性ハッシュ・監査ログ連鎖ハッシュのすべてがこの上に乗る。ここがずれると全既存取引IDが再現しなくなり、全件二重転記になる（設計書 CR-M 参照）。

## フェーズ1：振る舞い表で規定されたロジック
まだシート・Driveに触れない。入力を渡して出力を比べるだけ。

| 対象 | 振る舞い表 | ケース数 |
|---|---|---|
| 年補完 | 5.1 | 20 |
| 文字コード判定・文字化け検出 | 5.2 | — |
| 有効明細の判定 | 5.3 | — |
| B列の書込と読取確認の正準化 | 5.5 | — |
| 取引先判定 | 5.7 ＋ 5.14 辞書フィクスチャ | 12 |
| 変更検出 | 5.8 | — |
| 件数・合計照合 | 5.9 | — |
| 事前検証の区分判定 | 5.10 | — |
| 空き行判定・テンプレート行拡張 | 5.11 | — |
| 前年利用日判定 | 5.12 ＋ 5.15 | 12 ＋ 再判定5 |
| 外貨の任意列 | 5.13 | 8 |

**このフェーズを飛ばして先に進まないこと。** 表のケースが全部通ってから次へ行く。

## フェーズ2：データアクセス層
第2章のシート定義どおりに読み書きする層。`60_ProcessLog` / `61_TransactionLog` / `62_AuditLog` / 各マスター。

ここから並行性・冪等性の不変条件（INV-03/05/06/19/20/21）が効いてくる。

## フェーズ3：取込フロー
第6章のシーケンス。6.1（メイン）→ 6.2（再開）→ 6.3（要確認解決）→ 6.4（取消し）→ 6.5 → 6.6（形式登録）。

## フェーズ4：カード形式登録
第4章4.12（4.12.1〜4.12.10）。**単独で最大の機能。** サンプルからの下書き生成、3ゲート、コーパス回帰、再ベースライン。

初期4形式の定義値は 2.1.2.1 に投入済みだが、**実ファイルで検証されていない**（仕様8.4からの推定）。24.2の回帰試験が検証の関門になる。

# 3. 過去に繰り返し壊れた箇所

設計レビューで**複数回**再発した失敗。実装でも同じことが起きやすい。

## 3-1. 復旧経路を、無関係な検査で塞ぐ（3回再発 → INV-41）
「防護を追加する」変更として正しく見えるのに、別の経路を止める。3件とも**追加した側からは見えなかった**。

- 顧客別辞書と監査ログをオーナー限定にしたら、確認担当者が1ファイルも処理できなくなった
- コーパスフォルダの読取・書込検査を全メニューに掛けたら、同じことが起きた
- 対象年度の是正メニューが既定スコープに入り、コーパスの設定不備で塞がれた

**検証・権限・前提条件を追加するときは、必ず INV-41 と照合すること。** 4.6に検証項目を足す場合と4.2にメニューを足す場合は、契約上その確認が義務。

## 3-2. 参照する列・定数・設定が存在しない
本文に「〜を保存する」と書いてあるのに、シート定義にその列がない。設計レビューで7〜8箇所同時に起きた。

**実装時は逆向きに確認する。** 読み書きする列が第2章の定義表に実在するか。設定キーが4.1と第11章の両方にあるか。

## 3-3. 出口のない状態を作る
「詰んだら人が直せる」を確認せずに失敗経路を作る。形式登録まわりで4件同時に見つかった（放棄サンプル・解決不能な衝突・再ベースライン不能・回復メニュー不在）。

**失敗パスを書いたら、そこから人が抜ける手順がメニューから到達できるかを必ず確認する。**

## 3-4. 説明を読んでアルゴリズムを実装し、表で確かめない
年補完で5回起きた。**振る舞い表を先にテストコードへ写してから実装すること。**

# 4. 設計書が間違っていた場合

**黙って設計と違う実装をしないこと。** 設計書は5ラウンドのレビューを経ており、一見おかしく見える記述の多くには理由がある（第1章の判断表と、各節の「なぜこうしたか」を参照）。

矛盾・曖昧・実装不能を見つけたら：

1. まず第1章の判断表と当該節の理由書きを読む。既に検討済みの可能性が高い
2. それでも問題なら**報告する**。「設計書 §x.y の記述 A と §z.w の記述 B が矛盾する」「§x.y は実装不能。理由は〜」の形で
3. 判断を仰いでから直す。設計書と実装が食い違ったまま進めない

とくに**依存関係（第12章）に辺を増やす変更**は必ず報告すること。循環を作る可能性がある。Ver.2.5 では、依頼された修正が2箇所で循環を作ると判明し、別の構成に変えた実績がある。

# 5. 完成の定義

## モジュール単位
- 契約（第4章）の全関数が実装され、保証・事前条件・事後条件を満たす
- 当該モジュールが参照する不変条件（第3章の「主な参照モジュール」欄）を破らない
- 対応する振る舞い表の全ケースが通る

## システム全体
- **仕様25.1 の受入チェックリスト**（30項目超）をすべて満たす
- 第5章の各節の受入条件を満たす
- 10.3 のリリース手順の必須ゲートが通る：直列化ベクトル、取引先判定ベクトル、前年判定ベクトル、前年再判定ベクトル、コーパス回帰

## 障害注入
仕様23.4・24.3 が要求する8つの停止点（転記先シート・取引ログ・監査ログ・ファイル名変更の各書込の直前・直後）で停止させ、再実行で `COMMITTED` の重複行が増えず、`PREPARED`/`WRITING` が確定または要確認へ収束すること。設計書 4.39 にシームの定義がある。

# 6. 環境と制約

- **実行形態**：スプレッドシートに紐づくバウンドスクリプト。コードは**メニューを押した利用者の権限で動く**。これが 3-1 の失敗の原因なので常に意識すること
- **バージョン管理**：`clasp` ＋ Git。安定版タグを付け、ロールバックはタグの再反映（設計書10.3）。**Apps Scriptの「バージョン付きデプロイ」は参照されない**ので、デプロイ切替はロールバック手段にならない
- **実行時間**：6分上限。継続トリガーによる分割実行が設計済み（4.35）
- **テスト環境の分離**：仕様24.1。テスト実行主体から本番へ書き込めないこと
- **障害注入フラグ**：本番では常に無効。自己防衛ガードが 4.39 に規定済み
